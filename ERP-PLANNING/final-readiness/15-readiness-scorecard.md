# 15 — Final Readiness Scorecard

Scores reflect independently verified evidence, not planned/documented intent. Every score below 90 is explained. See the referenced document for full evidence and file:line citations.

| #   | Dimension              | Score | Rationale                                                                                                                                                                                                                                                                                                                                         |
| --- | ---------------------- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Architecture           | 82    | The 5-layer model is genuinely implemented, not aspirational (`03`). Deducted for the gap between "mechanism exists" and "mechanism fully applied" surfaced by the Manufacturing blockers.                                                                                                                                                        |
| 2   | Multi-tenancy          | 68    | JWT-layer isolation is excellent (evidence, no gaps found). RLS coverage (~2-3% of tenant tables) and the confirmed tenant-suspension no-op are real structural gaps at the database/lifecycle layer (`04`).                                                                                                                                      |
| 3   | Capability model       | 65    | Registry/guard design is fail-closed and well-tested where wired. Score is capped by 2 confirmed blockers directly inside this system (`05`).                                                                                                                                                                                                     |
| 4   | Entitlements           | 55    | The billing plan-change bug is a confirmed, reproducible regression of a previously-fixed defect, plus no transaction-wrapping and no audit trail (`05`, `10`). Lowest score in this scorecard by design — this is the least ready subsystem.                                                                                                     |
| 5   | RBAC                   | 78    | Permission naming is domain-generic; composition with capability checks is correct wherever both exist. Deducted for the closed-world vertical mechanism (5th vertical = code change) and for zero RBAC-denial logging (`05`, `09`).                                                                                                              |
| 6   | Frontend/navigation    | 88    | Nav filtering is centralized, correct, and honestly documented as non-authoritative. Deducted only for the one BOM/Work-Centers nav gap that mirrors the backend blocker, not a frontend defect in itself (`08`).                                                                                                                                 |
| 7   | Backend enforcement    | 62    | Excellent where wired (POS/HR_PAYROLL/INVENTORY_BATCH, each independently verified end-to-end). Capped hard by the Manufacturing capability-enforcement blocker — the platform's newest vertical is not actually protected by its own central enforcement mechanism (`05`).                                                                       |
| 8   | Domain reusability     | 84    | Core services (sales/inventory/purchase/production/accounting) are predominantly industry-agnostic; extension-table discipline is the norm. Deducted for one duplicated system (ProductionOrder/JobWorkOrder), one misplaced capability (PricingResolutionService), and one bolted-on-column exception (`07`).                                    |
| 9   | Industry extensibility | 75    | Architecturally proven twice (Distribution, Manufacturing) with no fork required in either case. Deducted because the platform's own most recent proof case is exactly where the enforcement/provisioning blockers live, and because Healthcare specifically would need net-new compliance infrastructure with no existing scaffold (`06`, `13`). |
| 10  | Data model             | 85    | Clean extension-table pattern is the norm; the schema/migration match for Business Profile Foundation showed zero drift despite that being a documented recurring bug class elsewhere in this codebase. Deducted for the one bolted-on-column exception and the India-only `hsnCode NOT NULL` constraint (`06`, `07`).                            |
| 11  | API architecture       | 83    | Consistent error shape, additive-not-invasive reusability pattern proven across 3 verticals. Deducted for the missing platform-wide idempotency convention and incomplete apiV2 uniformity (`08`).                                                                                                                                                |
| 12  | Event architecture     | 70    | Transactional outbox and idempotency are both genuinely correct — strong foundations. Deducted for the passive schema registry, the still-duplicated topic-derivation logic, and — most importantly — the consumer-side DLQ visibility gap, which directly threatens "can a new industry add events safely" (`08`).                               |
| 13  | Reporting              | 80    | Tenant safety is fully verified; the previously-reported report-registry/engine mismatch is confirmed fully reconciled. Deducted because "registry-driven" overstates the reality — every report still needs hand-written SQL (`08`).                                                                                                             |
| 14  | Search                 | 90    | Tenant isolation is structural (3 independent layers) and the extension pattern for new entity types is low-blast-radius. No deduction beyond the minor "config-driven" framing overstatement (`08`).                                                                                                                                             |
| 15  | AI Copilot             | 72    | Tenant/RBAC isolation is genuinely sound — the strongest isolation guarantee found anywhere in this audit (no direct DB access, JWT-inherited RBAC). Deducted for the hardcoded (non-pluggable) tool registry, zero capability-registry integration, and zero Prometheus metrics (`09`).                                                          |
| 16  | Security               | 70    | No cross-tenant leakage path was found anywhere. Deducted for RLS coverage, the tenant-suspension no-op, the one raw-SQL defect, and the unresolved dependence on undefined production network policy for internal-route exposure (`04`).                                                                                                         |
| 17  | Observability          | 58    | Health-check coverage is complete (18/18) and capability-denial logging/metrics are good. Lowest non-entitlement score because two of the audit's own example diagnostic questions ("why does Tenant X have Capability Y," "why was User Z denied") are **not answerable** today for the most common cases (`09`, `10`).                          |
| 18  | Scalability            | 72    | Per-tenant job isolation, RBAC evaluation cost, and nav-filtering cost are all architecturally sound (O(1)/cheap). Deducted for the confirmed O(N tenant × M job) scheduler-startup pattern and the dead L1 capability-cache tier (`10`).                                                                                                         |
| 19  | Backward compatibility | 93    | The one area with no blocker or high-severity finding. Existing cloth/grocery flows verified mechanically-additive-only; migration bookkeeping clean; 2 of 2 executed test suites pass at zero failures (`11`).                                                                                                                                   |
| 20  | Testing                | 66    | New test coverage is substantive where written, and executed suites pass cleanly. Score is capped because the exact tests that would have caught 2 of this audit's 3 blockers exist but are DB-gated and were very plausibly never run in this environment (`12`).                                                                                |

**Unweighted average: 75.6 / 100** — consistent with verdict C ("partially ready, important architectural work remains"): no dimension scores catastrophically (nothing below 55), but multiple dimensions central to the platform's own definition of "multi-industry ready" (Entitlements, Backend Enforcement, Observability) score in the 55-72 range, driven by concrete, evidenced, fixable findings rather than speculative concerns.
