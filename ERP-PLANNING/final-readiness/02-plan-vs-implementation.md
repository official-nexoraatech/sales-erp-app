# 02 — Plan vs. Implementation Cross-Check

Independent verification of the planning corpus (`ERP-PLANNING/multi-industry-platform/`, 24 docs, and `ERP-PLANNING/implementation/`, 4 phase directories) against live code — not against the documents' own claims about each other. Both trees are themselves currently uncommitted/untracked in git.

## Method note

The `ERP-PLANNING/implementation/phase-0N-*/` corpus is unusually self-auditing: each phase already contains an independent "post-implementation-review" document written by a different session than the one that built the code, itself re-deriving claims from `git diff`/test execution rather than trusting the implementation report. This audit's contribution is a **third, independent pass**, spot-checking both the original claims and the prior reviews' claims directly against the file system as it exists right now.

## Confirmed gap: work shipped without a phase-05+ planning directory

`ERP-PLANNING/implementation/` contains exactly 4 phase directories. **No `phase-05` or later exists.** Yet substantial, real code shipped after Phase 4 with no corresponding planning set:

- **Distribution** (migration 0172) — tracked instead in a separate `ERP-PLANNING/DISTRIBUTION-ROADMAP/` tree.
- **Manufacturing** (migrations 0174–0181, 5 new capability-registry entries) — tracked only informally, inside `16-phase-roadmap.md`'s Phase 12 section and code comments.
- **RLS enablement** (0176–0178) — tracked only via session memory, not a phase doc.
- **Partner Portal** (0182–0183) — tracked via the separate `CRM-ROADMAP` doc tree.

**This is a real, confirmed process/traceability gap.** The code itself is real and correctly built on the Phase 1–4 foundation (per the migration/schema cross-checks above) — the gap is documentation practice, not implementation quality. A second, compounding finding: `41-phase-2b-closure-review.md` (written 2026-08-20, before Manufacturing/Distribution/Partner-Portal shipped) already flagged that **three different phase-numbering schemes disagree with each other** (the source roadmap's Phase 0–12, a session-renumbering, and the `implementation/phase-0N-*` folder names) — this was never reconciled; both `00-roadmap-analysis.md` and `16-phase-roadmap.md` remain in their original, unreconciled state.

## Confirmed documentation-vs-code divergences

1. **`07-rbac-model.md`'s planned mechanism was silently abandoned before implementation began.** The doc specifies a `packages/shared-types/src/module-permissions.ts` file with `MODULE_PERMISSION_PREFIXES` (prefix-derived permission-to-module association). This file **does not exist anywhere** in the repo. Instead, `capability-registry.ts`'s `CapabilityDefinition` lists permissions directly per capability. `00-roadmap-analysis.md`'s own note explains why: "doc 21... collapsed the two-tier Module/Capability vocabulary... into one flat `CAPABILITY_REGISTRY`" before a line of the original design was built — `07-rbac-model.md` and `05-module-capability-model.md` describe the **pre-doc-21 design**, superseded before implementation, never updated to reflect the flat model actually built. This is the "documented-as-planned, silently replaced" variant of the pattern the audit brief asked to hunt for.

   Also independently confirmed: the flat model's own `permissions` field on each capability definition is **inert metadata**, read by zero runtime authorization code (`capability-guard.ts`'s `isCapabilityEnabled()` only reads `flagKey` and `requires`).

2. **`06-entitlement-model.md` cuts both ways** — undersells what shipped (lists `PaymentGatewayAdapter`, `tenant-billing-cycle` job, and billing admin UI as "not built"; all now exist, confirmed by file and matching prior PG-027 session memory), while correctly and still-accurately flagging `createTenantContextMiddleware` (tenant-suspension enforcement) as unregistered anywhere — a genuine, still-live no-op (see `04-multitenancy-security.md` §10).

3. **`19-first-industry-recommendation.md`** recommended Distribution as primary with Manufacturing as an acceptable parallel choice, explicitly "pending user confirmation." Both were in fact built — consistent with the doc's own framing (not a divergence). One genuine gap: no artifact records that user confirmation was ever actually obtained before either vertical was built; both planning trees proceed as if the recommendation were self-executing.

## Confidence summary

**High confidence** (direct grep/read against the exact claimed file): Phase 1 registry/guard existence and wiring count; Phase 2 migration + test existence; Phase 4 migration-vs-schema match; Manufacturing/Distribution business_types reuse; ADR-06; `module-permissions.ts` non-existence; `PaymentGatewayAdapter.ts` existence; `createTenantContextMiddleware` non-registration; phase-05+ directory absence.

**Medium confidence** (claim cross-referenced against code, but the actual test suite could not be executed — no reachable dev Postgres/Redis this session): Phase 3's real-DB integration tests exist and are substantive, but were not re-run to confirm they currently pass.

**Explicitly unchecked, not silently assumed**: R9 outbox-saga correctness; `14-api-strategy.md`'s exact service-routing count; line-by-line re-verification of every sentence in the remaining ~12 lightly-touched docs.
