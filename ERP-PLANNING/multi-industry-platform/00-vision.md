# 00 — Vision: Nexoraa Multi-Industry Platform

Status: Discovery/Planning only. No code changed by this document set.
Companion to (does not replace) `ERP-PLANNING/ERP_MASTER_SPEC.md`, which remains the architecture bible for what is already built.

## 1. Where Nexoraa is today

Nexoraa is a single-tenant-per-company, multi-tenant SaaS ERP running as ~17 Fastify/Drizzle microservices behind one API gateway, currently serving two verticals in production code: `CLOTH_RETAIL` and `GROCERY` (`tenants.vertical`, `packages/db-client/migrations/0164_tenants_vertical.sql`). It was originally built as a cloth-retail ERP (see `ERP-PLANNING/ERP_MASTER_SPEC.md`, phase-prompt naming) and has since had one vertical (Grocery) added by reusing the existing platform layer with no fork (`multi_vertical_grocery_audit_2026_08_16` — 245 of ~250 DB tables are already vertical-agnostic; only 5 cloth-specific tables exist and they're already isolated behind their own routes/flags).

## 2. Where it needs to go

One platform, one codebase, capable of onboarding new industries (Manufacturing, Distribution, Furniture, Restaurant, Bakery, Hotel, Healthcare, ...) by **configuration and additive domain modules**, not by forking or rewriting. Concretely:

```
Tenant → Business Profile → Industry → Business Type → Enabled Modules → Role → Permission → Feature Flag → Navigation → Domain Services
```

This is a refinement of what already exists, not a new idea grafted on. Section 3 below shows the gap between the target chain and what's actually wired today.

## 3. What's already true (do not rebuild)

These are load-bearing existing decisions this plan preserves as-is:

- **Tenant is root.** No Organization/Company-group table exists or is needed — confirmed by full schema review (`01-current-state.md` §1). Do not introduce one without new evidence.
- **JWT-only trust boundary.** The gateway never forwards `x-tenant-id`/`x-user-id` headers; every service independently re-verifies the JWT and derives tenant/user/permissions from it (`apps/api-gateway/src/middleware/gateway-auth.ts`, `01-current-state.md` §6). This is a deliberate, correct security boundary — any future capability/module-context propagation must ride inside the JWT or be re-derived per-service, never a trusted header.
- **RESOURCE_ACTION permission naming.** ~330 flat permission constants in `packages/shared-types/src/permissions.ts`, already module-prefixed by convention (`CRM_*`, `HR_*`, `GSTR1_*`, `PLATFORM_*`). Reuse the convention; do not rename.
- **Feature flags already exist and already work.** `PlatformFeatureFlags` (`packages/platform-sdk/src/feature-flags.ts`) — 2-tier cache (in-memory 30s + Redis 300s), per-tenant override over global default, hot-invalidated via Redis pub/sub. ~20+ flags already seeded, dotted-namespace keys (`pos.enabled`, `hr.payroll.enabled`, `gst.e-invoice.enabled`).
- **A plan/entitlement primitive already exists and is partially built.** `plan_entitlements` (global tier template) + `tenants.plan`/`tenants.settings.maxUsers/maxBranches` + `BillingService.assignPlanEntitlements()` (`apps/tenant-service/src/domain/BillingService.ts`) copies a plan's flags/limits onto a tenant — this is Session 1 of PG-027; Sessions 2–3 (payment gateway, billing-cycle job, admin UI) are not built. See `06-entitlement-model.md`.
- **Application-level tenant isolation, not RLS.** Every tenant-scoped table has `tenant_id` + explicit `WHERE` filters via `TenantScopedDatabase`. RLS was designed (`infrastructure/docker/postgres/init.sql`) but never enabled — deliberately deferred per `ES-36_COMPLETION.md` because the session GUC isn't set outside explicit `.transaction()` blocks, and most routes don't use one. See `13-security-architecture.md`.
- **A `vertical` column already exists** (`tenants.vertical`, added 2026-08-16 per `multi_vertical_grocery_audit_2026_08_16`), but it is a 2-value label consumed at **provisioning time only** (role/feature-flag/chart-of-accounts seeding) — nothing reads it at request time to gate module visibility. This is the seed the target Business Profile model grows from, not a competing concept to remove.

## 4. What this plan does NOT propose

Per the governing brief and confirmed by evidence, this plan explicitly does not:

- Introduce an Organization/Company-group layer.
- Replace `tenants.vertical` outright — it evolves it (see `03-target-architecture.md` §2, `15-migration-strategy.md`).
- Rename the RESOURCE_ACTION permission system.
- Enable Postgres RLS as part of this initiative (recommendation only — see `13-security-architecture.md`).
- Build a backend navigation microservice.
- Introduce gRPC, a metadata-driven low-code engine, or per-industry forked services.
- Implement billing/payment-gateway integration (PG-027 Sessions 2–3) as part of this work — flagged as a parallel, separately-scoped initiative.
- Pick Hotel by default — see `19-first-industry-recommendation.md` for an evidence-based evaluation.
