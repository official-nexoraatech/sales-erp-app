## Process used for every module (established on Sales, repeated on Inventory)

1. Two parallel research agents: one audits every real frontend page/dialog/form/button/status
   in the module (with file:line references, no speculation), one traces real backend
   cross-module effects (accounting/GST/inventory/reports impact, with file:line references).
2. Fix real, safe, contained UX bugs found (delete confirmations, mislabeled actions, raw
   IDs shown instead of names, missing empty states, broken/fictional tour claims).
3. Flag — but do not blind-fix — large/risky backend bugs (e.g. wrong RBAC redesign, broken
   raw-SQL reports, missing accounting integrations) since fixing those without a live DB/stack
   to verify against risks introducing new incorrect behavior, which is worse than flagging it.
4. Write/update tour content: deep "complete guide" tours (`type: 'complete'`) for pages with
   real workflow complexity, lighter updates for simple master-data CRUD pages. Every business-
   impact claim in tour copy must trace to a specific finding from step 1, never invented.
5. Wire missing `data-tour-id` targets (extending shared components like `ERPRowAction`/`Badge`
   to forward tour-id/native props when needed, rather than duplicating markup per page).
6. Add status-badge hover tooltips and field-level `hint`/`description` props on forms.
7. Verify: `pnpm type-check` (monorepo-wide), `eslint --quiet` on touched paths, `vitest run`
   on both the DAP suite and the touched backend service's own suite.
8. Update this document, then move to the next module without stopping for confirmation
   (per explicit instruction — working autonomously overnight).

## Foundational DAP engine work (already shipped, applies to every module)

- Route-pattern matching (`sales/invoices/:id`-style) in `TourProvider.navigateToStep` and
  `HelpPanel`'s "This page" discovery — lets detail-page tours spotlight real status-transition
  buttons instead of only describing them in prose.
- `calloutTitle`/`calloutVariant` on `TourStep` — lets the same bullet-box UI serve as Business
  Impact (info/blue), Common Mistakes (warning/amber), Best Practices (success/green).
- `InfoTooltip` component (`components/ui/InfoTooltip.tsx`) for field-level contextual help
  outside the tour system.
- `Badge` forwards native props (`title` for hover tooltips); `ERPRowAction` has an optional
  `tourId` field forwarded as `data-tour-id` on inline row-action buttons.
- Dedicated "Guided Tours" header icon (Compass), separate from the general Help icon —
  `TourGuidePanel.tsx`, sharing `TourLaunchButton` with `HelpPanel`.
- `useHasUnseenPageTour` — pulsing dot on the Guided Tours icon when the current page has a
  tour the user has never started/skipped/completed.
- P0 height/centering bugs in `TourTooltipCard`/`useFloatingTourPosition` fixed (affected every
  centered step across all tours, not module-specific).
- No tour step anywhere forces a real DOM click to advance (`mode: 'interactive'` removed from
  all content) — a guided tour is a passive walkthrough, never requires actually submitting a
  real form/creating real data just to read the next step. Enforced by a registry-wide test.

- `apps/web-frontend/e2e/live-dap-tour.spec.ts` already covers both real cross-module workflow

  earlier precedent (asking before starting even a single low-memory dev server) and the standing
  memory note that this machine has a real ceiling on repeated full-stack restarts, doing this
  without the user available to watch for a hung boot or OOM is a materially riskier and less
  reversible action than anything else done autonomously tonight. The static test suite above
  (185 vitest assertions, including the new 133-test route-existence check) is the safe substitute
  that could be run unsupervised and gives real signal that tour content didn't drift from the app.
- **Recommended follow-up for the user**, next time they're available: run the full `live-*.spec.ts`
  Playwright suite (including `live-dap-tour.spec.ts`) against the real running stack to get actual
  browser-verified confirmation of every tour's spotlighted targets — the static route-existence
  test proves routes exist, but does not prove every `target` CSS selector still resolves to a real
  DOM element (e.g. a button that was renamed or removed rather than a page that moved).
