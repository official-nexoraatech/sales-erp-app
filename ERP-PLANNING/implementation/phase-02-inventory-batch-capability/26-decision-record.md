## D1 — Sales-service valuation-engine reconciliation (BLOCKING — must be decided before any code is written)

### Recommendation: **(B) — migrate `apps/sales-service` onto the shared `@erp/sdk` engine.**

This is a recommendation per the brief's explicit request for one on this decision — it is **not** authorization to proceed. The user must confirm before implementation begins, because (B) is the larger, riskier change (R2 below) and touches live, high-transaction-volume financial code (invoices, POS, sales returns). It should ship as its own isolated phase (**2A**, see `25-revised-scope.md` §6) with a dedicated behavioral-equivalence test pass, merged and stable _before_ the capability-gating work (2B) that makes `fefoEnabled` settable — gating a still-diverged engine would reproduce the exact defect this review found, just with extra steps.

**Why not (A) despite being smaller**: (A) requires re-adding `batchNumber`/`expiryDate` to the local interfaces and re-implementing tested ordering logic from scratch — at that point, most of the actual engineering work of a migration has been done anyway, just to arrive at a permanently-duplicated, permanently-divergence-prone result. The brief's own framing ("the long-term goal is one coherent ERP platform, not divergent industry/service implementations") points directly at (B).

## D2 — Expired-stock lifecycle (business decision — OPEN, not resolved by this planning pass)

**This is explicitly not decided here.** Full per-flow analysis: `29-expiry-policy-analysis.md`. Summary: current code (both engines) never blocks consumption of already-expired stock — FEFO only reorders preference, it does not gate. Three options exist (hard block / warn-and-allow / configurable policy), and they may reasonably differ by flow (a sale of expired stock is a different risk than an internal stock adjustment writing off expired stock). **The user must choose a policy per flow, or explicitly ratify "no gating, ordering-preference only" as the intended v1 scope**, before Phase 2C (if it proceeds) is planned in file-level detail. Phase 2A/2B do not require this decision to proceed, provided the "FEFO does not block expired stock" limitation is explicitly documented and communicated (see `28-financial-impact-analysis.md` §6, R4 in `32-revised-risk-register.md`).

## D3 — Batch-targeted correction workflows (non-blocking, follow-up candidate)

Should stock adjustments, physical-verification write-offs, and purchase returns eventually support targeting a _specific_ batch/layer (by `batchNumber`/layer ID) rather than aggregate item+warehouse quantity? Confirmed gap: `StockAdjustmentService`, `PhysicalVerificationService.approve()` (`PhysicalVerificationService.ts:288`), and `PurchaseReturnService`'s `ReturnLineInput` all operate at aggregate item+warehouse granularity today — none has a `batchNumber`/`fifoLayerId` field, so the system (via FEFO/FIFO order), not the operator, decides which layer absorbs an adjustment, write-off, or return. Not required for Phase 2A/2B's acceptance criteria. **Recorded as an explicit "yes, follow-up" or "no, not needed" decision the user should make when convenient — not resolved here, but not silently left unaddressed either.**

## D4 — Capability-disable behavior for already-`fefoEnabled` items (non-blocking, recommendation carried forward from the original plan, restated for confirmation)

What happens to an item's `fefoEnabled = true` state if the tenant's `INVENTORY_BATCH` capability is later disabled (plan downgrade, admin toggle)?

- **(a) Leave item-level flags as-is** — items keep consuming FEFO-ordered even with the capability off; the column, not live capability state, drives `ValuationService`. Matches existing precedent (disabling `HR_PAYROLL` doesn't delete existing payroll records) and requires no new infrastructure.
- **(b) Force-revert** all of a tenant's `fefoEnabled` items to `false` on capability-disable — cleaner "off means off" semantics, but requires new event-driven infrastructure (a flag-disable listener) that doesn't exist for any other capability today.

**Recommendation: (a)**, unchanged from `15-security-impact.md` §4's original reasoning — still sound, still not disputed by the gate review. Restated here as formally requiring the user's confirmation before Phase 2B ships, per CLAUDE.md's instruction not to silently pick even when a recommendation is offered.

## Capability boundary — confirmed, no split

Explicit determination requested by the brief: are batch tracking, expiry tracking, and FEFO one capability or three?

**One capability — `INVENTORY_BATCH` — confirmed, not split.** Reasoning (per `24-pre-implementation-review.md` §5, independently re-verified against the current registry — `capability-registry.ts` confirmed to have zero existing batch/expiry/FEFO entries, so this is a greenfield choice, not a migration of an existing split):

1. The single source of truth the engine reads is one column, `items.fefoEnabled` — there is no independent "expiry tracking enabled" or "batch tracking enabled" flag anywhere in the schema, and no evidence any tenant would want expiry data captured but FEFO ordering not applied, or batch numbers tracked without expiry.
2. GRN batch/expiry _capture_ is already unconditional/always-on (REUSABLE DOMAIN, not gated at all, per `03-capability-definition.md` §1) — it isn't part of the capability boundary question at all, since it never needs gating.
3. Splitting into three capabilities for "theoretical flexibility" with no evidence of demand is exactly what the brief's own instruction ("do not split them merely for theoretical flexibility") prohibits.

**One addition to the boundary definition this revision makes explicit** (identified as missing from the original plan, `24-pre-implementation-review.md` §5): the boundary is **uniform across all consumption flows**, not just sales. A batch-tracked item's stock is FEFO-ordered everywhere it's consumed — sales, POS, sales returns, transfers, adjustments, physical verification, purchase returns, job-work material issue — not only at the point of sale. Partial FEFO (obeyed for sales but not transfers) would be incoherent and confusing. This must be stated as the intended boundary in `03-capability-definition.md` going forward, not left to be discovered as a side effect (see `27-affected-flow-matrix.md` for the flow-by-flow consequence).
