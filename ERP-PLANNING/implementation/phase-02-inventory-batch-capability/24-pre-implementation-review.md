## 1. Executive Verdict

**NOT READY.**

The plan's central technical premise — "FEFO consumption ordering does not exist anywhere in the codebase; this phase adds it to `ValuationService.consumeFifoLayers`" (`01-current-code-evidence.md` §4, restated in `04-domain-model.md` §2, `05-service-impact.md` §3, `21-file-level-change-plan.md` Step 3, `23-executive-summary.md` §2 point 2) — **is factually wrong.**

FEFO consumption ordering is **already fully implemented**, tested, and live in `packages/platform-sdk/src/valuation-engine.ts` (`consumeFifoLayers`, lines 339–371: `ORDER BY (expiryDate IS NULL), expiryDate ASC, receivedAt ASC` when `fefoEnabled` is true), with its own dedicated test suite (`packages/platform-sdk/src/__tests__/valuation-engine-fefo.test.ts`). It is the active consumption engine for `inventory-service` (stock transfers, adjustments, physical verification), `purchase-service` (GRN, purchase returns), and `production-service` (job-work orders).

What the plan's own evidence-gathering missed: `apps/sales-service` has a **second, stale, un-migrated duplicate** of the same class — `apps/sales-service/src/domain/ValuationService.ts` — which still orders purely `asc(receivedAt)` (line 243) with zero reference to `expiryDate`/`batchNumber`/`fefoEnabled`. This is the file the plan read and correctly described. It is **not** the only such file in the repo, and the plan never discovered the other one. Directly confirmed: `apps/sales-service/src/domain/InvoiceService.ts:32` imports `ValuationService` from the **local** `./ValuationService.js`, not `@erp/sdk` — even though the same file imports other utilities from `@erp/sdk` on line 28. `InvoiceService.confirm()` is the shared code path for both regular invoices and POS checkout (`apps/sales-service/src/api/pos.routes.ts:435-442` calls it directly), and `SaleReturnService.ts` uses the same local copy for sales-return restocking.

This is not a minor correction. It means:

- The actual engineering problem this phase must solve is **not** "add a conditional `ORDER BY` clause" — it's **"reconcile a live, already-diverged duplicate of a financial consumption engine used by every sale, POS checkout, and sales return in the system."** That is a materially different, larger, and riskier piece of work than a one-line ordering change, and it directly recreates the exact "ledger services duplicate domain logic, confirmed drift bugs" pattern this codebase has hit before (session memory: `architecture_no_cross_service_valuation`) — the very failure mode this plan's own `15-security-impact.md`/`22-risk-register.md` never considers, because it didn't know the duplicate existed.
- Once this gap is closed and `fefoEnabled` becomes settable, **behavior on already-live, always-on routes changes silently and untested**: stock transfers, stock adjustments, physical verification, purchase returns, and job-work order consumption all run through the already-FEFO-aware `platform-sdk` engine today (dormant only because no item can currently be flagged) and are not mentioned anywhere in the plan's testing strategy (`16-testing-strategy.md`), file-level change plan (`21-file-level-change-plan.md`), or service-impact analysis (`05-service-impact.md` claims 3 services affected; the real number, once the capability is live, is at least 4 — `production-service` is un-mentioned and affected).
- The plan's claim that reordering is "invisible at any API boundary... same total quantity consumed, same COGS calculation, only _which_ layer rows are decremented first changes" (`07-api-contracts.md` §4) is **false** whenever consumed layers carry different unit costs — the normal case. Total COGS for a transaction changes when layer-selection order changes across layers of differing cost. This is a financial-correctness claim, stated as settled, that is not actually true.
- A real, unaddressed business-semantics gap exists that the plan's own cited justification (pharma/food-safety/regulatory traceability, `02-business-requirements.md` §3) makes serious: **nothing in the current or proposed design prevents selling, transferring, adjusting, or returning already-expired stock.** FEFO only changes _which_ batch is picked first — it does not gate expired stock from being consumed at all. For the exact verticals the plan cites as the motivating business case, this is the difference between "sell oldest-expiring first" (implemented) and "never sell expired" (not implemented, not discussed).

None of this means the phase is wrongly conceived — `INVENTORY_BATCH` is still a reasonable, well-scoped next capability, and most of the registry/RBAC/migration/frontend-nav/entitlement work in this plan is sound and can proceed close to as written (see §2). But the plan cannot be authorized for implementation as currently written: its domain-model, service-impact, testing-strategy, and risk-register sections are built on an incorrect premise about what already exists, and the required fix touches a live financial subsystem the plan never analyzed.

**Recommendation: NOT READY. Return to planning for a re-scoped `04-domain-model.md`/`05-service-impact.md`/`16-testing-strategy.md`, and require the user to make one explicit architectural decision (§15) before any code is written.**

## 3. Business Semantics Review

Answering the 19 required questions from directly-verified code (not assumed):

1. **Source of expiry date**: GRN line at receipt only (`grn.routes.ts` line 26 schema field, threaded through `GRNService.ts:396-408`). No other source exists.
2. **Is expiry mandatory for batch-tracked items?** **No, and not enforced anywhere.** A GRN line's `batchNumber`/`expiryDate` are both optional regardless of the receiving item's `fefoEnabled` value — nothing in `GRNService.ts` or the GRN schema conditions on the item flag. A tenant could mark an item batch-tracked and still receive stock with no batch/expiry captured on some or all GRN lines. Not addressed by the plan.
3. **Can a batch exist without expiry?** Yes — `expiryDate` nullable; `NULLS LAST` ordering handles this gracefully in consumption, but see §2 above — this is silent, not validated.
4. **Can an expiry date be changed after capture?** **No edit path exists anywhere** in the repo (grep for `UPDATE`/writes to `inventoryFifoLayers.expiryDate`/`batchNumber` — only consumption (`remainingQty`) and landed-cost (`unitCost`) updates exist, `valuation-engine.ts:239-241`). Once written, immutable. If a supplier's label is misread at receipt, there is no correction path.
5. **Can a batch number be changed?** Same as above — no.
6. **How is batch quantity maintained?** `inventory_fifo_layers.remainingQty`, decremented under row-level `FOR UPDATE` lock during consumption (see §8 Data Consistency).
7. **How does stock consumption select batches?** Via `consumeFifoLayers`: `ORDER BY (expiryDate IS NULL), expiryDate ASC, receivedAt ASC` when `fefoEnabled`, else `receivedAt ASC` — **but only in the `inventory-service`/`purchase-service`/`production-service` code path**. `sales-service`'s local copy ignores `fefoEnabled` entirely (§1, §2). This is the phase's real gap to close.
8. **Insufficient quantity in earliest-expiry batch?** Confirmed the function locks and iterates multiple candidate layer rows in order, consuming across as many as needed — continues to the next eligible layer automatically (both copies of the engine do this).
9. **Continues to next eligible batch?** Yes, confirmed by the same loop logic.
10. **What happens to expired stock?** **Nothing.** No status flag, no auto-block, no auto-write-off anywhere in the schema or code. `nearExpiryAlert.job.ts` only _notifies_; it does not restrict anything.
11. **Can expired stock be sold?** **Yes — nothing prevents it.** FEFO only changes _ordering preference_, it is not a _guard_. A batch past its `expiryDate` remains fully consumable through every existing sale/POS/transfer/return path with `remainingQty > 0`.
12. **Can expired stock be transferred?** Yes, same reasoning — `StockTransferService` performs no expiry check.
13. **Can expired stock be adjusted (written off)?** Yes, but **not surgically** — adjustments and physical-verification write-offs operate on aggregate item+warehouse quantity only (`StockAdjustmentService`, `PhysicalVerificationService.ts:288`), with no line-item field to target a specific `batchNumber`/layer ID. The system, not the operator, decides which layer absorbs the write-off (via FEFO/FIFO order) — which may not be the specific expired batch a physical count actually found.
14. **Can expired stock be returned (to supplier)?** Only incidentally — `PurchaseReturnService`'s `ReturnLineInput` has no `batchNumber`/`fifoLayerId` field (confirmed, no such field in the interface); the consumption call (`consumeForStockOut`) picks whichever layer FEFO/FIFO order selects, which is not necessarily the batch physically being sent back.
15. **Partial quantities**: handled correctly — confirmed via the locking/loop logic in §8.
16. **Two batches, same expiry**: deterministic secondary sort by `receivedAt ASC` (confirmed in the `ORDER BY` clause).
17. **Deterministic tie-breaker**: `receivedAt`, confirmed as above.
18. **Missing expiry dates**: `NULLS LAST`-equivalent (`expiryDate IS NULL` sorts last) — layers without an expiry are consumed after all layers that have one, in `receivedAt` order among themselves. Deterministic.
19. **Cannot determine FEFO order at all** (e.g., no `fefoEnabled`): falls back cleanly to pure FIFO-by-`receivedAt` — the base case, deterministic, unchanged from today.

**Verdict**: Questions 1, 3, 5(no), 6–9, 15–19 are cleanly and deterministically answered by existing code. Questions 2, 4, 10–14 are **not resolved by the plan and not by current code** — several of these (10, 11, 14) are direct, material gaps against the plan's own stated business justification (regulatory traceability for pharma/food). These must be recorded as open decisions (§15), not silently left for a future phase, since "expiry-aware" without any expired-stock guard is easy to misread as "expired stock is protected," which it is not.

## 4. FEFO Review (Capability-Specific)

The core mechanism (ordering, tie-breaking, partial-quantity handling, NULLS-last semantics) is well-designed and already proven correct in `platform-sdk`'s engine and its dedicated test file. The defect is **not** in the ordering algorithm — it's in:

1. **Reach**: only 3 of 4 live consumption call sites (inventory-service, purchase-service, production-service) use the FEFO-aware engine; `sales-service` (invoices, POS, sales returns) does not.
2. **Guardrails**: FEFO orders but does not gate. No expired-stock protection exists anywhere, for any consumption path, FEFO-aware or not.
3. **Correction paths**: batch number and expiry date are immutable and unvalidated at capture (no future-date check, no uniqueness constraint on `batchNumber` per item/warehouse in `inventory_fifo_layers`' indexes — confirmed only non-unique indexes exist).

## 5. Capability Boundary Review

`03-capability-definition.md`'s classification (item toggle + ordering = INDUSTRY CAPABILITY; GRN capture = REUSABLE DOMAIN/always-on; FIFO/valuation itself = CORE; alerting = CORE) is **precise and correct** — this is one part of the plan that does not need rework. It correctly avoids the "ambiguous umbrella" failure mode the brief warns about.

One boundary question the plan does not address explicitly, now that the true reach is understood: **does `INVENTORY_BATCH` gate consumption behavior for stock transfers, adjustments, physical verification, purchase returns, and job-work orders, or only sales?** Given the item-level `fefoEnabled` flag is the single source of truth read by the shared engine, the only coherent answer is **all of them, uniformly** — a batch-tracked item's stock should be FEFO-ordered everywhere it's consumed, not just at the point of sale. This is almost certainly the _right_ design (partial FEFO — "obeyed for sales but not transfers" — would be worse and confusing), but it must be **stated as the intended boundary**, not discovered as a side effect, and the testing/acceptance criteria must cover it (§14).

## 8. Data Consistency Review

**Concurrency**: independently verified as safe in both engine copies. `consumeForStockOut` locks the `items` row `FOR UPDATE` first, then `consumeFifoLayers` locks all candidate `inventory_fifo_layers` rows `FOR UPDATE` before mutating `remainingQty`, all inside a single DB transaction per caller (`InvoiceService.ts:514`'s `this.db.transaction`, `StockTransferService.ts:155`, etc.). **Two concurrent FEFO consumers cannot double-allocate the same layer** — the second transaction blocks on the row lock until the first commits or rolls back. This directly answers the brief's explicit concurrency question: **not possible under the current design**, in either engine copy. No severity classification needed — this part is sound.

**Immutability gap**: batch number and expiry date, once written, cannot be corrected (§3 Q4/Q5) — a data-entry error at GRN receipt is permanent. Not a race condition, but a real operational gap worth flagging as a risk (§13).

**No validation on expiry date**: no future-date check, no format validation beyond ISO datetime string; no uniqueness constraint on `batchNumber` per item/warehouse — duplicate batch numbers for the same item/warehouse are structurally permitted. Both are pre-existing GRN-capture gaps, not introduced by this phase, but this phase is the first to make batch/expiry data _decision-relevant_ (previously it was inert metadata) — the bar for data quality on this data just rose, and the plan doesn't address it.

## 9. Backward Compatibility

The plan's zero-behavior-change guarantee for existing tenants (`17-migration-and-backward-compatibility.md`) **holds for what the plan actually changes** — no existing item can have `fefoEnabled = true` today, so the conditional branches it adds are inert until an admin explicitly opts an item in, and the permission-backfill mechanism (targeting the real `role_permissions` table, independently confirmed to exist at `packages/db-client/src/schema/auth.ts:92-105`, with working precedent at migration `0070_es35_es37_role_defaults_permission_backfill.sql`) is technically sound and additive-only.

What the guarantee **does not cover**, because the plan didn't know about it: the moment the write-path gap closes and a real tenant flags a real item, behavior changes silently on the five always-on routes in §6 that the plan never analyzed. "Zero behavior change for existing tenants" is only true in the narrow sense of "no _currently configured_ item's behavior changes" — it says nothing about what happens the first time any tenant (existing or new) actually uses the feature, which is the entire point of shipping it. The plan should extend its backward-compatibility analysis to cover first-use behavior on all affected routes, not just pre-use inertness.

**Existing Grocery and Clothing/Retail tenants**: confirmed unaffected pre-use, consistent with the plan's claim, for the reasons above.

## 10. Security Review

- **Tenant isolation**: confirmed correct throughout — `tenantId` is sourced from `request.auth`/JWT in every route/service inspected across all four services (GRN, purchase return, invoice, item routes), never from body/query/params.
- **Branch/warehouse isolation**: confirmed via `getBranchScope(req.auth)` on GRN routes; `StockTransferService`/`ValuationService` methods take `warehouseId` as an explicit param threaded from auth-derived context, not client-supplied in a way that bypasses scope.
- **Capability enforcement fail-closed behavior**: `isCapabilityEnabled()` confirmed to have no internal try/catch (`capability-guard.ts`) — the plan's requirement that the new in-handler call site in `item.routes.ts` must itself wrap the call and fail closed (`15-security-impact.md` §2) is necessary and correctly identified; this is not yet code, so it remains an implementation-time requirement to verify, not a pre-existing guarantee.
- **Direct-service access**: unchanged trust model — every new/modified route still requires a valid JWT verified locally by the service, consistent with the existing, proven-safe pattern.
- **Frontend as security boundary**: confirmed not violated — `enabledCapabilities`/`capabilityKey` remain UX-only; no backend code reads client-supplied capability state (consistent with Phase 1's own verified finding, unchanged by this phase's scope).
- **New gap found, not addressed by the plan**: the near-expiry-alert internal route (`stock.routes.ts:52-74`) uses a shared-secret header (`x-internal-key` compared via `timingSafeEqual`) with **no tenant context at the route level at all** — the job queries globally across all tenants and relies entirely on downstream event payloads carrying correct `tenantId`. This is pre-existing (not introduced by this phase) and the plan correctly leaves this route untouched, but it's worth noting the asymmetry against the new user-facing route's proper `authenticate → requireCapability → requirePermission` chain, in case a future reviewer assumes both internal-facing and user-facing near-expiry surfaces share the same trust model. They don't.

No new trust boundary, no gateway logic change, no RLS change — consistent with the plan's claims.

## 12. Scope Review

The registry/RBAC/migration/frontend-nav/entitlement portions of this plan are correctly sized — small, additive, low-risk, and should **not** be expanded. Do not fold `MULTI_UOM` in (correctly deferred). Do not fold in `HR_PAYROLL`/`POS` route-wiring (correctly deferred). Do not build any expired-stock lifecycle/blocking feature as part of this phase (that would be scope creep) — but it **must** be recorded as an explicit, named gap and open decision (§15), not silently deferred without a paper trail, since the plan's own business justification implies it.

What belongs in a **follow-up**, not this phase, once the core sales-service reconciliation is resolved:

- Batch-targeted (not aggregate-only) adjustment/write-off and purchase-return flows (§3 Q13/Q14) — real gap, but a larger UI/API surface change, correctly out of this phase's size.
- Expiry validation (future-date check, batch-number uniqueness) at GRN capture — small, could arguably ride along with this phase's migration but is not required for the phase's stated acceptance criteria; flag as a fast-follow.
- Expired-stock guardrails (block/warn on sale, transfer, etc. of expired batches) — this is a genuinely separate, larger feature (business-rule engine territory) and correctly does not belong in this phase, but the _absence_ of it must be documented as a known limitation of "FEFO" as delivered, not conflated with "expiry protection."

What does **not** belong in this phase but is currently silently absorbed into it by omission: reconciling `sales-service`'s duplicate valuation engine. This is not scope creep to add — it is the actual, unavoidable core of what "wire FEFO onto sales-service" requires, once the premise is corrected. It cannot be deferred to a later phase, because the phase's own acceptance criteria (`20-acceptance-criteria.md` items A–I, especially D "backend service enforcement works" and F "existing tenants remain unaffected") are not achievable without it — shipping the write-path (`fefoEnabled` becomes settable) without fixing sales-service's consumption path would mean a tenant can configure an item as batch-tracked, see it reflected in the UI, and have their actual sales/POS/return transactions silently ignore that configuration — a worse, more confusing state than not shipping the feature at all.

## 15. Open Decisions

Per CLAUDE.md §1 and the brief's explicit instruction not to silently resolve architectural or business decisions, the following must be decided by the user before implementation:

**D1 — Sales-service reconciliation approach (blocking, must be decided before any code is written).**

- **(a) Migrate `apps/sales-service` onto the shared `@erp/sdk` `valuation-engine.ts`**, removing the local duplicate entirely. Pro: eliminates the duplication permanently, matches the direction of the recent `d7de8ca` Trial-Balance/P&L/BS/Cash-Flow engine consolidation. Con: larger, riskier change touching `InvoiceService.ts` (invoices + POS) and `SaleReturnService.ts` — both live, high-transaction-volume financial code paths; requires careful behavioral diffing between the two implementations first (§13 R2).
- **(b) Patch the local `sales-service/ValuationService.ts` copy in place** to add the same conditional FEFO ordering, leaving the duplication intact. Pro: smaller, more surgical, matches the plan's original size estimate. Con: perpetuates a known-risky duplication pattern (`architecture_no_cross_service_valuation`), and the two copies can (and, per R2, may already) diverge in other ways that this doesn't fix.
- This plan has not surfaced this choice at all, because it didn't know the duplicate existed. It must be presented to the user as a real decision, not defaulted silently to either option.

**D2 — Expired-stock lifecycle (non-blocking for this phase, but must be recorded).**
Does "FEFO" as delivered by this phase need to also gate (warn or block) consumption of already-expired stock, or is "prefer earliest-expiring first, with no hard stop" the intended v1 scope? The plan implicitly assumes the latter by omission. Given the plan's own stated business case (pharma/food-safety traceability), this should be a conscious, recorded product decision, not a gap discovered later by a Distribution/Pharmacy tenant in production.

**D3 — Batch-targeted correction workflows (non-blocking, follow-up candidate).**
Should adjustments, physical-verification write-offs, and purchase returns eventually support targeting a _specific_ batch/layer rather than aggregate item+warehouse quantity? Not required for this phase's acceptance criteria, but worth an explicit "yes, follow-up" or "no, not needed" decision rather than leaving it unaddressed indefinitely.

**D4 — Already carried forward from the plan itself, restated for completeness**: what happens to an item's `fefoEnabled = true` state if the tenant's `INVENTORY_BATCH` capability is later disabled (`15-security-impact.md` §4's option (a) vs (b))? The plan's own recommendation (leave as-is) is reasonable and this review does not dispute it, but it remains formally undecided pending user confirmation, per the plan's own framing.

## 16. Final Implementation Authorization Recommendation

**NOT READY.**

The capability choice (`INVENTORY_BATCH`), its boundary definition (§5), its registry/RBAC/migration mechanics, and its frontend delivery pattern are all sound and require little to no rework. The blocking defect is narrow but load-bearing: the plan's evidence-gathering missed an existing, tested, already-live implementation of the exact behavior it set out to build, misdiagnosed the remaining gap as a one-line change to the wrong file, and as a direct consequence under-scoped the service impact (missed `production-service`, mischaracterized `purchase-service`), under-scoped the testing strategy (missed 5 of 9 affected always-on routes), and overstated the financial neutrality of the change it's making.

**Path to READY**: address the eight items in §14, obtain the user's decision on D1 (and ideally D2), and resubmit the revised `01-current-code-evidence.md` §4, `04-domain-model.md` §2, `05-service-impact.md`, `07-api-contracts.md` §4, and `16-testing-strategy.md` for a follow-up gate review. The registry/RBAC/migration/frontend portions of this plan do not need to be re-reviewed if unchanged — only the consumption-ordering domain-model and its downstream sections do. This should be achievable as a scoped revision, not a full re-plan, and the phase remains, in principle, the right next step for the roadmap once correctly scoped.
