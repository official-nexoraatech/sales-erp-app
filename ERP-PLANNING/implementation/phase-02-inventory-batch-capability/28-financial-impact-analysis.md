# 28 — Financial Impact Analysis

Corrects `07-api-contracts.md` §4's claim that reordering is "financially neutral... same COGS calculation, only _which_ layer rows are decremented first changes." That claim is false whenever consumed layers carry different unit costs — the normal case, not an edge case. This document is the analysis `24-pre-implementation-review.md` §14 item 6 required.

---

## 1. The mechanism — why ordering changes money, not just sequence

`consumeFifoLayers` (`packages/platform-sdk/src/valuation-engine.ts:339-412`) decrements `inventory_fifo_layers.remainingQty` across one or more layer rows until the requested quantity is satisfied, summing `qty_consumed_from_layer × layer.unitCost` as it goes. FIFO orders this by `receivedAt`; FEFO orders it by `expiryDate` (NULLS last, tie-break `receivedAt`). **Whenever two candidate layers for the same item/warehouse have different `unitCost` values — which happens routinely (different purchase price across GRNs, landed-cost adjustments, price fluctuation) — selecting a different layer first produces a different weighted-average cost for the transaction.** This is not a hypothetical: it is the direct, intended consequence of choosing FEFO over FIFO, and it is inseparable from the feature actually doing what it's for (prioritizing near-expiry stock for movement, regardless of whether that stock happens to be the cheapest layer).

## 2. Where this surfaces — the direct chain to the general ledger

Confirmed by direct code read this session:

```
InvoiceService.confirmInTransaction()  [sales-service, InvoiceService.ts:623-631]
  → ValuationService.consumeForStockOut(trx, {...})   [layer selection + cost calc happens here]
  → lineCogs accumulated per line, cogsPerUnit = lineCogs / lineQty   [:631]
  → invoiceCogsTotal += lineCogs, aggregated across all lines         [:811]
  → COGS_CALCULATED outbox event emitted with cogsTotal
       ↓
CogsAccountingConsumer.handleCogsCalculated()  [accounting-service]
  → cogsTotal = Number(p.cogsTotal ?? 0)        [:23 — trusts the number as-is, no recomputation]
  → PostingMatrixService.buildJournalEntry({ eventType: 'COGS_CALCULATED', amount: cogsTotal, ... })
  → JournalEngine.post(...)                      [DR Cost of Goods Sold / CR Inventory, :46]
```

**accounting-service does not recompute COGS and has no visibility into which engine or which ordering produced the number it posts.** It is implementation-agnostic in code, but not in the number it receives — a change to the _selection order_ in `ValuationService` becomes a change to the _journal amount_ accounting-service posts, automatically and without any accounting-service code change. This confirms: **`AccountingService` does not need to be modified for this phase.** The financial-correctness question is entirely upstream, in which valuation engine sales-service uses and how it orders consumption (D1).

## 4. Does this alter financial results for existing tenants?

**No, not retroactively, and not for any tenant until they explicitly opt in — but yes, prospectively, once they do.**

- No existing item has `fefoEnabled = true` today (confirmed impossible — zero write path exists before this phase). Every historical transaction's COGS was computed under FIFO and is not recalculated or restated by this phase.
- The moment an admin explicitly flags an item `fefoEnabled: true` (post-Phase-2B), **every subsequent stock-out consumption for that item, across all nine flows in `27-affected-flow-matrix.md`, uses FEFO ordering from that point forward.** This is a real, immediate, and intentional change in that item's future COGS/valuation behavior — not a bug, the feature working as designed.
- Because the two engines have already diverged (sales-service's local copy has _never_ honored `fefoEnabled`), fixing D1 is itself a **prospective-only correction**: it does not retroactively adjust any invoice already confirmed. It only changes behavior for stock-outs that happen after the fix ships.

## 5. Rollout strategy

1. **Ship D1 (Phase 2A) first, in isolation, before any item can be flagged `fefoEnabled: true`.** Since no item can reach that state before Phase 2B's write path exists, Phase 2A carries **zero** financial-behavior change for any tenant on merge — it only makes the two engines behaviorally equivalent for the FIFO case (proven by the required regression suite, `26-decision-record.md` D1) and FEFO-capable for the case that doesn't exist yet.
2. **Ship Phase 2B (capability gating) second.** From this point, financial behavior changes only for items an admin explicitly opts in, and only from that point forward.
3. **Communicate the "not financially neutral" fact to the item-level toggle's UI/documentation** — an inventory manager flipping `fefoEnabled: true` on an item should understand this changes future COGS sequencing for that item, not just alerting/sort order. This is a documentation requirement on Phase 2B's frontend work (`09-navigation-and-frontend.md`), not a new engineering task.

## 6. Tenant migration implications

None required. This is additive, opt-in, per-item — there is no tenant-wide migration or bulk-recalculation step. A tenant with zero `fefoEnabled` items after Phase 2B ships sees zero financial change, indefinitely, until they choose otherwise.

## 7. Historical vs. prospective transaction behavior

- **Historical** (already-confirmed) transactions: immutable, unaffected. `inventory_fifo_layers` rows already consumed keep their recorded `remainingQty`/`unitCost` history; nothing in this phase rewrites past ledger rows.
- **Prospective** transactions: as of D1's merge, both engines behave identically for `fefoEnabled=false` (the only state possible until Phase 2B). As of Phase 2B + an explicit per-item opt-in, prospective transactions for that item use FEFO ordering.

## 8. Audit requirements

No new audit infrastructure needed. The existing generic before/after diff mechanism on `PUT /items/:id` (confirmed by the original plan, `24-pre-implementation-review.md` §11, unchanged by this revision) already captures `fefoEnabled` toggles. Each `COGS_CALCULATED` event already carries `invoiceId`/`invoiceNumber` and posts through the standard `JournalEngine`, which has its own existing audit trail — no new field or mechanism required to trace a given journal entry back to the invoice and item that produced it.

## 9. Reconciliation requirements

None beyond what already exists. Because this phase does not retroactively alter any historical COGS figure, there is no reconciliation exercise required against prior periods. The only new operational practice worth recommending (not a code requirement): when an admin first enables `fefoEnabled` on a high-volume item, a finance reviewer may want to spot-check the next few transactions' COGS against expectation — a process recommendation, not a system requirement, and out of this phase's engineering scope.

## 10. Should `AccountingService` be modified?

**No.** Confirmed by direct code read: `CogsAccountingConsumer.ts` is already fully decoupled from the valuation engine's internals — it posts whatever `cogsTotal` it receives, regardless of which engine or ordering produced it. The analysis above proves the correct fix is entirely upstream (D1, `26-decision-record.md`), not in accounting-service. This satisfies the brief's explicit instruction: "Do NOT modify AccountingService unless the analysis proves it is required" — it does not.
