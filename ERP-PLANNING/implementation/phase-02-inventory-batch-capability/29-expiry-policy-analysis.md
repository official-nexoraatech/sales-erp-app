# 29 — Expiry Policy Analysis

**This document does not decide a policy. Per the governing brief and CLAUDE.md §1, this is recorded as D2 — an explicit OPEN DECISION requiring business input this planning pass cannot supply.** It exists so the decision, once made, has a ready-made analysis to act on, and so "no decision" doesn't silently default to a policy no one chose on purpose.

---

## 1. What exists today (confirmed, both engines)

Nothing blocks, warns on, or restricts consumption of already-expired stock, anywhere, in either the shared engine or the local sales-service duplicate. FEFO (`consumeFifoLayers`) only changes _which_ layer is preferred; it never checks whether the selected layer's `expiryDate` has already passed. A batch past its expiry date remains fully consumable — sellable, transferable, adjustable, returnable — through every existing path, so long as `remainingQty > 0`. This is confirmed, not assumed, by direct reading of `valuation-engine.ts` (no `expired`/expiry-gating logic found anywhere in the file) and independently by the gate review's business-semantics review (`24-pre-implementation-review.md` §3, Q10-Q14).

**The gap that makes this a real decision, not a hypothetical**: the phase's own stated business justification (`02-business-requirements.md` §3) is pharma/food-safety/regulatory traceability. For those verticals specifically, "sell oldest-expiring first, with no hard stop" and "never sell expired stock" are materially different guarantees, and a Grocery, future Distribution, or future Pharmacy tenant could reasonably assume FEFO implies the latter. It does not, today, in any form.

## 2. The three options

**(A) Hard block** — any attempt to consume (sell/transfer/adjust/return) a layer whose `expiryDate` has passed is rejected with an error, forcing the operator to resolve it explicitly (e.g., write it off first).

**(B) Warning / allow** — the system surfaces that a selected layer is expired (in the response, a flag, a UI banner) but does not prevent the operation from completing.

**(C) Configurable policy** — a per-tenant or per-item setting chooses between (A) and (B) (and possibly "no check" as a third state), since different verticals/regulatory contexts have different requirements.

## 3. Per-flow evaluation

## 4. Cross-cutting observations (not a decision)

1. **A single global policy is unlikely to be right.** The analysis above shows sale/POS/production have real regulatory exposure where a hard block is defensible, while adjustment/physical-verification are the _resolution_ mechanism for expired stock and should probably never be blocked. This asymmetry is itself evidence in favor of (C) — configurable, likely at minimum by flow-category (customer-facing vs. internal-resolution), not necessarily by tenant.
2. **A hard block requires an escape hatch.** Every real-world inventory system with expiry blocking still needs a supervised override path (e.g., a permission-gated "confirm despite expiry" action) — pure hard block with no override tends to get worked around informally (bypassing the system) rather than respected. This has downstream RBAC implications (a new permission) not scoped by this document.
3. **This is business-rule-engine territory, not a small addition.** Per `24-pre-implementation-review.md` §12: implementing any of A/B/C properly (per-flow, with override paths, with UI surfacing) is a genuinely separate, larger feature — correctly out of Phase 2A/2B's scope, and correctly not silently folded in.
4. **The absence of a decision is itself a decision, and must be recorded as such.** If the user does not choose a policy now, Phase 2A/2B ship with the implicit "no gating, order-preference only" behavior that exists today — this must be explicitly documented (not silently left as an unstated assumption) as the current v1 behavior in the capability's own description/UI copy, so a tenant configuring `fefoEnabled: true` doesn't reasonably-but-wrongly assume expired stock is now protected. See `28-financial-impact-analysis.md` §5 and `32-revised-risk-register.md` R4.
