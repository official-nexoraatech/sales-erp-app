| E   | Frontend navigation responds to capability state                   | Near-Expiry Stock nav item hidden/shown per `enabledCapabilities`, proven by `navigation.test.ts`; manually verified in-browser toggling the flag on a test tenant (per CLAUDE.md's UI-testing requirement)                                                                                                                                                                         |

| G   | The capability can be used by a genuinely different business model | Documented reuse path for Distribution/Manufacturing/Bakery (`02-business-requirements.md` §3) — not independently testable in this phase since those business types don't exist yet, but the capability's design has zero Grocery/Cloth-Retail-specific logic anywhere in its implementation (confirmed by code review: no `vertical`/business-type branching in any touched file) |
| H   | The implementation does not require an industry fork               | Confirmed by construction — capability lives across `inventory-service`/`sales-service`, zero new service, zero new deployable, zero new gateway route (`05-service-impact.md` §5)                                                                                                                                                                                                  |
| I   | The same capability infrastructure can support future industries   | `CAPABILITY_REGISTRY` grows from 2 → 3 entries using the identical pattern Phase 1 established, with zero change to `requireCapability`/`isCapabilityEnabled`/the frontend delivery mechanism themselves — proves the registry scales without touching the mechanism, the central claim of `21-capability-resolution-architecture.md`                                               |

## Additional phase-specific criteria

- FEFO consumption-ordering test passes: an item with `fefoEnabled: true` and two FIFO layers of differing `expiryDate`/`receivedAt` consumes the earlier-expiring layer first, even when it wasn't received first.
- An item with `fefoEnabled: false` (or omitted, the default) shows **zero** change in consumption ordering versus pre-phase behavior — the exact same test cases Phase 1-era `ValuationService` tests already assert, still passing unmodified.
- `erp_capability_check_denied_total` increments correctly from the new in-handler call site (`18-observability.md` §1), not just the route-level preHandler sites.
- Full `turbo run type-check` and `turbo run test --continue` clean (modulo the same pre-existing, independently-confirmed-unrelated failures Phase 1 documented).
