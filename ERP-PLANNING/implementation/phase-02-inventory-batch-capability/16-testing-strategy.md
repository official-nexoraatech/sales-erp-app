# 16 — Testing Strategy

## 1. Registry / guard reuse — no new test needed for the mechanism itself

`capability-registry.test.ts`'s cycle-check/completeness tests and `capability-guard.test.ts`/`capability-guard-route.test.ts`'s outcome-matrix tests (Phase 1, 25 tests, all passing per `21-post-implementation-review.md` §9) already generically prove `requireCapability`/`isCapabilityEnabled` correctness for _any_ registry entry, including this phase's new `INVENTORY_BATCH` one — only the registry-completeness test needs to pass against the updated registry (automatic, no new test file).

## 3. Regression proof (following Phase 1's exact discipline, `20-implementation-report.md` §13)

Before merge: `git stash -u`, re-run the pre-existing failing suites (`@erp/hr-service`, etc. — the known `turbo_parallel_test_false_failures`/`concurrent_sessions_on_same_repo` class), confirm byte-identical pre-existing failures, restore stash. Full `turbo run type-check` across all packages. Full `turbo run test --continue`, confirm only this phase's touched packages (`@erp/types`, `@erp/sdk`, `inventory-service`, `purchase-service` [unchanged, but run anyway], `sales-service`, `tenant-service`, `auth-service` [unchanged, verify], `web-frontend`) show new passing tests, zero new failures.

## 4. DB+Redis integration test

Extend Phase 1's still-not-executed `capability-resolution.integration.test.ts` gap (`21-post-implementation-review.md` §10) — this phase should **not** repeat the same "written but never run" gap. If Docker/local Postgres+Redis is available at implementation time, run both Phase 1's and this phase's integration tests together against real infra before treating either as fully proven; if not available, document the same honest limitation Phase 1 did, not silently skip mentioning it.

## 5. Manual verification (per CLAUDE.md's UI-testing requirement)

Start the dev server. On a tenant with `INVENTORY_BATCH` disabled: confirm the item form shows no batch/expiry section, confirm "Near-Expiry Stock" doesn't appear in the nav. Toggle the flag on for that tenant (admin route or direct DB update in dev): confirm both appear without a re-login being required to see the nav change is **not** expected yet (Phase 1's known limitation, `enabledCapabilities` only refreshes on full login, `21-post-implementation-review.md` §5 — re-login and re-verify). Mark an item `fefoEnabled: true`, receive two GRNs with different expiry dates, issue a partial sale, confirm the earlier-expiring batch's `inventory_fifo_layers.remainingQty` decreases first even though it wasn't received first.
