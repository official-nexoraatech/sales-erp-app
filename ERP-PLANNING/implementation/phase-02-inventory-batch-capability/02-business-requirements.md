## 2. Why `INVENTORY_BATCH` and not `MULTI_UOM` as the first capability

Both are real, both are currently dead code (schema shipped, unreachable — `01-current-code-evidence.md` §3, §6). `INVENTORY_BATCH` is chosen as the **first** because:

1. It has a genuine, verifiable **correctness gap**, not just a missing toggle: FEFO consumption-ordering doesn't exist (§4 of `01-current-code-evidence.md`). Proving the capability means proving it actually changes behavior correctly when turned on — a stronger test of "not merely a demo flag" (the brief's explicit requirement) than `MULTI_UOM`, whose conversion-factor math is a simpler, more mechanical gap.
2. It spans three services with zero shared code path (`01-current-code-evidence.md` §10) — the strongest available proof that capability enforcement doesn't imply a service boundary, directly exercising `21-capability-resolution-architecture.md` §1's rule.
3. It has a real near-expiry alerting feature already fully working (`nearExpiryAlert.job.ts`) that becomes meaningfully more valuable once FEFO ordering exists (alerting on expiring stock is only useful if the system also _tries_ to sell it first) — giving this phase a genuine, motivating business story, not just an architecture exercise.
4. `MULTI_UOM` is a clean fast-follow using the identical pattern this phase establishes (registry entry → complete plumbing → gate → nav), explicitly flagged as such in `00-overview.md` §6 and `23-executive-summary.md`.

## 3. Who needs this capability (the "genuinely different business model" requirement)

- **Grocery (existing tenant type)**: perishables — dairy, produce — are the textbook FEFO use case. This capability directly improves an existing vertical's correctness, not just a future one's.
- **Distribution**: batch/lot tracking is close to mandatory for FMCG/pharma distributors (regulatory traceability in many product categories) — a real commercial requirement, not a nice-to-have.
- **Manufacturing (future)**: raw-material lot tracking for quality/recall traceability is a standard MRP requirement — this capability's data model (item-level opt-in, lot/expiry on stock layers) is exactly the primitive a future BOM/material-consumption system would consume, not something that would need to be rebuilt.
- **Bakery/Pharmacy (future, per `19-first-industry-recommendation.md`)**: named directly as candidates that "exercise Phase 7's Commerce Core generalization... under a different pattern" — this phase **is** that generalization work, completed properly instead of left half-built.
- **Cloth Retail (existing tenant type)**: does not need this — and correctly won't get it, since the flag defaults to the tenant's business-type-appropriate value (see `17-migration-and-backward-compatibility.md` — default ON matches current de facto behavior for GRN capture, but the _item-level_ `fefoEnabled` toggle stays `false` until a tenant/admin explicitly opts an item in, so no cloth-retail item's behavior changes).

## 4. What "done" looks like for the business

A Grocery or Distribution tenant's inventory manager can mark a perishable/lot-tracked item as batch-tracked (`fefoEnabled: true`) through the existing item-edit screen; from that point, GRN receipts continue to capture batch/expiry as they already do, stock issuance for that item prefers the earliest-expiring batch first (not just the earliest-received), and a new "Near-Expiry Stock" report page shows what's approaching expiry — all gated behind one capability that a tenant's plan/business-type can turn on or off without any code change, and completely invisible/unavailable to a tenant that doesn't have it (a Cloth Retail tenant sees nothing new).
