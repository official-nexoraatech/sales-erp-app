## What "enforcement" adds, conceptually

Phase 1 built _resolution_ (can we correctly compute true/false for a given tenant+capability) and _the guard function_ (can we correctly deny a request when resolution says false). Neither capability has ever had that guard function actually attached to a route. This phase adds exactly one thing per route: a `requireCapability(key, ...)` entry in that route's existing `preHandler` array, positioned before the existing `requirePermission`/`requireAnyPermission` check, per the ordering `07-rbac-model.md` §4 and Phase 1's own `capability-guard-route.test.ts` already established and proved (capability check first — cheaper failure, clearer error).

No new `CapabilityDefinition` field, no new resolution logic, no new error code. The three-outcome contract (`CAPABILITY_NOT_ENABLED` / existing `FORBIDDEN` / `CAPABILITY_RESOLUTION_UNAVAILABLE`) from Phase 1 is reused byte-for-byte.
