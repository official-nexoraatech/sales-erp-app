**Financial trace (Rule 8):** payroll run creation → `PayrollEngine` → `payroll_slips`/salary computation → (per `02-gap-analysis.md`/existing architecture) accounting integration for salary expense posting. **Cross-module dependency check (Rule 7):** `InvoiceService.confirm()` (the real POS-sale write path, called by `pos.routes.ts:320`) is shared with the non-POS invoice-creation path (`invoice.routes.ts`) — confirmed by reading `InvoiceService.ts` in the Phase 2A work already reviewed this repo cycle. **This phase gates the POS _route_, not `InvoiceService` itself** — a non-POS invoice created through `invoice.routes.ts` is completely unaffected by `POS` capability state, by construction (the gate lives in `pos.routes.ts`'s preHandler array, never inside `InvoiceService`). This must be verified again at implementation time (read `InvoiceService.ts` fresh, don't assume Phase 2A's read is still current) but the architectural boundary is correct as designed.

**What reads/writes/reports on POS data, checked per Rule 7:**

- Reads: `report-service` (sales reports, likely aggregate over all invoices including POS-originated ones, not POS-route-specific — unaffected, since it reads `invoices` table data already written, not the route).
- Search: `search-service` indexes items/customers, not POS sessions — unaffected.
- Events: `InvoiceService.confirm()` emits its existing domain events regardless of which route called it — unaffected (see `11-event-impact.md`).
- AI Copilot: checked in `14-ai-copilot-impact.md`.

## Explicitly excluded from this phase's route-gating scope

- `employee.routes.ts` (in-handler field check, not a route gate — §3 of `01-current-code-evidence.md`).
- `loyalty.routes.ts` (no live `POS_*` check found).
- Any `apps/hr-service` route outside `payroll.routes.ts` (attendance, leave, employee lifecycle — these are core HR record-keeping, not gated by `HR_PAYROLL`, and have no capability of their own in this phase).
- `apps/pos-frontend`'s own request-signing/session logic — unaffected by a backend 403 change beyond needing to handle the new error code gracefully (`09-navigation-and-frontend.md` §9).
