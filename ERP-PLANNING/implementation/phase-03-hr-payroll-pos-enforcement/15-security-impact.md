# 15 — Security Impact

Structured as the same bypass-vector checklist Phase 1's (`21-post-implementation-review.md` §7) and Phase 2B's (`41-phase-2b-closure-review.md` §7) reviews used, applied to this phase's 18 routes.

| Vector                                         | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Direct service access**                      | The mechanism is unchanged, proven safe twice already (Phase 1 mechanism-level, Phase 2B real-route-level). This phase's only novelty is applying it to routes with real, active traffic — a rollout-safety question (D1), not a mechanism-security question.                                                                                                                                                                                                |
| **Gateway access**                             | Unchanged — `api-gateway` is not touched by this phase, same as Phase 1/2B.                                                                                                                                                                                                                                                                                                                                                                                  |
| **Frontend manipulation**                      | `enabledCapabilities` (web-frontend) / any future pos-frontend equivalent is UX-only, read by zero backend code — confirmed by the same grep pattern Phase 1/2B used, re-run for this phase's files: `payroll.routes.ts`, `pos.routes.ts`, `day-end.routes.ts`, `promotion.routes.ts` contain zero references to `enabledCapabilities`/`capabilityKey` in request-reading code (verify at implementation time; not yet re-run against files not yet edited). |
| **Modified request data**                      | `tenantId` at every gated call site comes from `(request as AuthedRequest).auth.tenantId` (JWT-derived), never a route param/query/body field — same pattern as every existing gated route in this codebase.                                                                                                                                                                                                                                                 |
| **Tenant switching**                           | No tenant-switching UI/API exists (unchanged finding, re-confirmed by Phase 1 and Phase 2B, not re-derived from scratch this session but no code change anywhere in this phase's scope would introduce one).                                                                                                                                                                                                                                                 |
| **Stale auth state**                           | `enabledCapabilities` on `web-frontend`'s session can go stale until next full login (Phase 1's known limitation, unchanged) — a UX staleness issue only, since the backend never trusts it.                                                                                                                                                                                                                                                                 |
| **AI Copilot**                                 | `14-ai-copilot-impact.md` — inherits protection via the same forwarded-JWT mechanism, no bypass.                                                                                                                                                                                                                                                                                                                                                             |
| **Background execution (scheduler/Kafka)**     | The two internal payroll routes (`/internal/payroll/prepare`, `/internal/payroll/send-slips`) are **not** gated by this phase (D2) — they remain `requireInternalKey`-only. This is not a bypass of the _capability_ check (nothing bypasses a check that was never applied to them), but it does mean a disabled tenant's scheduled payroll job would still run if triggered — an explicitly recorded, non-blocking gap (D2), not a silent one.             |
| **Internal service calls (`x-internal-key`)**  | Confirmed: `isCapabilityEnabled`/`requireCapability` are never called from any `x-internal-key`-guarded route in this phase's scope — consistent with Phase 1/2B's finding that this remains true platform-wide.                                                                                                                                                                                                                                             |
| **Cross-role escalation via capability state** | A `SUPER_ADMIN`/`OWNER` user is denied identically to any other role when the tenant-level capability is off (`08-permissions-and-rbac.md`) — capability state cannot be worked around by holding a higher-privilege role, since it's tenant-scoped, not role-scoped. Confirmed by the mechanism's existing design (`isCapabilityEnabled` takes `tenantId`, never a role), not a new check added by this phase.                                              |

## New consideration this phase surfaces that Phase 1/2B's checklists didn't need: entitlement-bypass risk if D1 is skipped or done wrong

If enforcement ships **without** D1's plan-derived backfill (or with a wrong/incomplete one), the actual security property this phase claims to add — "a tenant only gets POS/Payroll if their plan entitles them to it" — is not actually achieved; a tenant could remain incorrectly `true` (over-entitled, the pre-existing tenant-1-shaped gap direction) or incorrectly `false` (under-entitled, an availability regression, the primary D1 risk). **This phase's core security value (closing an unenforced entitlement gap) is only realized if D1 is resolved correctly** — this is the central reason D1 is a blocking decision, not a nice-to-have refinement.

## No new attack surface

Zero new routes, zero new trusted headers, zero new database write path from this phase's own code (only, conditionally, from D1's backfill migration, which is a one-time, reviewed, idempotent data correction — not an ongoing new surface).

**No bypass found in the mechanism itself** — consistent with Phase 1/2B. The residual risk here is entirely in _rollout correctness_ (D1), not in the enforcement mechanism, which was already proven twice.
