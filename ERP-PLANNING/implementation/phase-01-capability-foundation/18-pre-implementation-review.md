## 5. Capability Resolution Review

- **Tenant capability AND user permission are independent**: confirmed by design (`05-platform-sdk.md` §7 — two separate preHandlers, composed in an array, neither calls the other). No coupling found or introduced.
- **`CAPABILITY_NOT_ENABLED` vs `PERMISSION_DENIED`**: correctly designed to reuse the existing `{error:{code,message,details}}` envelope (§4 above confirms this envelope is real and consistently used); the two codes are semantically distinct in the response, matching the existing `FORBIDDEN`/`UNAUTHORIZED` code-string convention. One open decision remains — HTTP status (§16).
- **Dependencies required?** No — `requires: []` is valid and is what both of Phase 1's real registry entries use. Composition exists for future capabilities that need it.
- **How resolved?** Recursive `isCapabilityEnabled` walk: own flag AND all `requires` entries' resolved value, short-circuiting on first `false`.
- **What happens when a dependency is disabled?** The dependent capability resolves `false` too (fails closed transitively) — same `CAPABILITY_NOT_ENABLED` response, no separate error code distinguishing which layer failed (a deliberate simplicity choice, documented in `02-capability-model.md` §4).
- **Circular dependencies prohibited?** Yes, by a unit test walking the static registry's `requires` graph at test time (not a runtime check, since the registry is fixed code) — confirmed appropriate given the registry is not dynamically editable.
- **Fail-closed?** Yes, confirmed at every layer: unknown capability key → `false`; `PlatformFeatureFlags`'s own documented "missing flag defaults to disabled" behavior → inherited for free; no fail-open exception exists anywhere in the design.
- **Tenant isolation guaranteed?** Yes — `isCapabilityEnabled` takes `tenantId` only from `request.auth.tenantId` (verified JWT claim, never client-supplied), and delegates to `PlatformFeatureFlags`, whose isolation was independently re-confirmed in §4.

No changes required to this section's design.

## 6. Feature Flag Review

- **Can existing feature flags represent capabilities?** Yes — confirmed the schema (`tenantId` nullable, `flagKey`, `enabled`) has no structural limitation preventing this use.
- **Limitations found**: the two real race windows in `invalidate()`/`getValue()` (§7) are inherited, not introduced. A capability's effective state can theoretically be stale for up to the L2 TTL (300s) under the write-after-invalidate race, not just the documented L1 TTL (30s) — this is a real, previously-undocumented nuance worth stating precisely rather than the softer "at most 30s" claim in `04-capability-resolution.md` §3. **Correction applied**: none made to that file's wording in this pass (the 30s claim is the _common_ case, not the worst case) — flagged here as a precision note for future hardening rather than rewritten, since re-deriving the exact worst-case bound is a larger analysis than this gate review's scope justifies, and the existing flag system already lives with this same imprecision today for every other flag-gated behavior in the app. Not a new risk Phase 1 introduces.
- **Does the plan accidentally make `feature_flags` the permanent capability model?** No — `02-capability-model.md` §3 explicitly designs `CapabilityDefinition.flagKey` as an indirection layer specifically so the underlying storage could change without breaking callers of `requireCapability`/`isCapabilityEnabled`. Confirmed this indirection is real in the actual code sketch (`05-platform-sdk.md` §2) — nothing outside `capability-guard.ts` ever references `feature_flags` directly.
- **Reversible/evolvable?** Yes — see above. No second parallel flag system is created; confirmed by the file-level change plan touching zero schema.

## 7. Entitlement Review — genuine findings from this pass

**BillingService partial-write race (new finding, not in the original plan):** `assignPlanEntitlements` is not transaction-wrapped. `tenants.plan` commits before the per-flag insert/update loop runs; a crash or error mid-loop leaves a tenant with an inconsistent plan-vs-flags state (new plan recorded, only some of its flags applied). **Assessment: real, pre-existing, out of scope for Phase 1 to fix** — Phase 1 adds a docblock comment to this file only (`07-entitlement-integration.md` §3) and touches zero of its logic. Recommend a follow-up hardening ticket (wrap the loop in `this.db.transaction(...)`, matching the pattern already used elsewhere in this same service, e.g. `branch.routes.ts:160`) — not blocking, since this phase's own scope doesn't call `assignPlanEntitlements` or add new callers of it.

**Feature-flag cache write-after-invalidate race (new finding):** traced two concrete interleavings (Window A: read-during-invalidation-in-flight; Window B: a slower reader re-poisoning L1/L2 with a stale value fetched just before another process's invalidate/write completes) in `PlatformFeatureFlags.invalidate()`/`getValue()`. **Assessment: real, pre-existing in code this phase reuses as-is, not worsened by this phase** — Phase 1 introduces no new writer to `feature_flags`, so it doesn't create new race opportunities; it inherits whatever staleness risk already exists for every other flag-gated behavior in the app today. Documented, not fixed, consistent with this phase's stated non-goal of building new invalidation machinery (`07-entitlement-integration.md` §5).

**Previously-unlisted writer confirmed**: `apps/auth-service/src/routes/feature-flags.routes.ts`'s `PUT /admin/feature-flags/:name` is a second, real, production writer to per-tenant `feature_flags` rows (already referenced in `07-entitlement-integration.md` §4 as "the existing ops-driven toggle path," but this pass confirms it by direct code read rather than by inference). **New edge case found**: nothing prevents this ops route from writing to a tenant's flags while that same tenant is still mid-`PROVISIONING` (i.e., while `BillingService.assignPlanEntitlements`'s loop may still be running as part of `TenantProvisioner`'s flow) — an unguarded interleaving between two different services' writers to the same `(tenantId, flagKey)` rows. **Assessment: low-severity, pre-existing, theoretical** (requires an admin to specifically target a tenant still mid-provisioning, a narrow operational window) — flagged for the same future hardening ticket as the transaction gap, not a Phase 1 blocker.

**Upgrade/downgrade/revocation path**: confirmed **no route exists today** to trigger any of these for an existing tenant (only one call site of `assignPlanEntitlements`, at provisioning). `07-entitlement-integration.md`'s framing ("this is currently a theoretical problem") is correctly validated, not weakened, by this pass's deeper look.

**Cache invalidation / event propagation**: confirmed no event is published on entitlement assignment (zero `publish()`/`PlatformEventBus` references in `BillingService.ts`), matching the original plan's finding exactly.

**Conclusion for this section**: BillingService remains safe to treat as the sole authoritative writer for Phase 1's purposes — the races found are real but pre-existing, unreachable through any code path this phase adds, and appropriately deferred to a follow-up hardening item rather than blocking this phase.

## 17. Decision Record (2026-08-18)

Five decisions, approved by the architect after this review, applied to every affected planning document. (Decision 5 was added in a follow-up correction to Decision 4 — see below — and supersedes Decision 4's original two-outcome fail-closed design.)

**Decision 1 — Frontend capability delivery.** The frontend consumes capability information from the existing authenticated-user bootstrap mechanism (`authApi.me()` → `GET /users/me`, `apps/auth-service/src/routes/users.ts:551`), not a reconstruction from flags/entitlements/billing state, and not a new JWT claim. Backend `requireCapability()` remains the sole security boundary; frontend capability data is explicitly UX-only (navigation filtering, route visibility, capability-aware messaging). Applied to: `08-frontend-navigation.md` §2, `17-file-level-change-plan.md` (all "Only if Option B approved" rows), `00-overview.md`.

**Decision 2 — Capability error status.** `CAPABILITY_NOT_ENABLED` → HTTP 403. `PERMISSION_DENIED` → HTTP 403. Neither 402 nor 404 used. An honest discrepancy is documented (not silently resolved): today's live `requirePermission` actually emits `code: 'FORBIDDEN'`, not `PERMISSION_DENIED` — this phase introduces the new `CAPABILITY_NOT_ENABLED` code without renaming or touching the existing guard. Applied to: `11-api-contracts.md` §2–3, `00-overview.md`.

**Decision 3 — Pre-existing hardening risks stay out of Phase 1.** `BillingService.assignPlanEntitlements`'s missing transaction wrapping and `PlatformFeatureFlags`'s write-after-invalidate cache race are not fixed by this phase. Tracked in a new file, `19-deferred-hardening-risks.md`, so they aren't lost between sessions. Applied to: `19-deferred-hardening-risks.md` (new), `00-overview.md`, `11-api-contracts.md` (cross-reference).

**Decision 4 — Fail closed, including on resolution error.** _(Original form, 2026-08-18 — superseded in its specific response-code choice by Decision 5 below; the underlying fail-closed principle it established stands unchanged.)_ Beyond the already-designed "clean `false` → deny" path, `requireCapability` wraps its resolution call in an explicit `try/catch`: any thrown error (DB/Redis failure, unexpected exception) is caught and the request is denied, never allowed to propagate as an uncaught `500`.

**Decision 5 — Distinguish "capability disabled" from "capability resolution failure" (correction to Decision 4, 2026-08-18, same day).** Both are denials (fail-closed is unchanged as the governing principle), but they are different operational states and must be distinguishable in the response, not collapsed into one contract:

- **Capability disabled** (resolution succeeded, definitively `false`) → **403 `CAPABILITY_NOT_ENABLED`** — unchanged from Decision 4/2's original intent.
- **Permission denied** (capability enabled, user lacks permission) → the **existing, unmodified** live contract (**403 `FORBIDDEN`**) — this phase does not rename it to `PERMISSION_DENIED` and does not touch `requirePermission`. This corrects Decision 2's original write-up, which had incorrectly presented `PERMISSION_DENIED` as a decided/target code for the existing guard.
- **Capability resolution failure** (DB/Redis/infra/config error, state genuinely unknown) → **503 `CAPABILITY_RESOLUTION_UNAVAILABLE`** — a new, distinct outcome. Never reported as `CAPABILITY_NOT_ENABLED`, since that would misrepresent an infrastructure outage as a deliberate plan restriction.

Applied to: `04-capability-resolution.md` §5 (rewritten for the three-way split), `05-platform-sdk.md` §2 (code sketch updated — `catch` block now returns 503, distinct log line/level), `11-api-contracts.md` §2–4 (three-outcome contract, explicit `FORBIDDEN`-unchanged note), `12-testing-strategy.md` §1 and §3 (test lists rewritten for four preHandler outcomes / six route-level scenarios), `14-observability-and-audit.md` §1–2 and §7 (two log levels, metric now labelled by `outcome`), `16-acceptance-criteria.md` (criteria rewritten for three outcomes).
