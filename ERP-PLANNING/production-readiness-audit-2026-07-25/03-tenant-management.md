# Tenant Management Module — Fresh Production-Readiness Audit

Date: 2026-07-25
Scope: `apps/tenant-service` (tenant/org/branch/RBAC-defaults/SSO-config) + `apps/web-frontend/src/pages/admin` (Tenants*) + `apps/web-frontend/src/pages/settings` (Organization/Branches/Warehouses). Warehouse CRUD itself lives in `apps/inventory-service` (`/warehouses`), touched here only because the Settings UI groups it with Branches.

Methodology: no prior audit claims were trusted without re-verification. Every item below was either (a) exercised live against the running stack (gateway :3000, tenant-service :3011, auth-service, inventory-service, real Postgres, real MinIO) with a newly created, then safely torn-down, test tenant, or (b) confirmed by direct source read where live exercise wasn't practical (e.g. the approval-workflow authorization fix, which requires standing up a multi-step workflow instance). A prior 2026-07-22 "Tenant Service Enterprise Audit" existed in `ERP-PLANNING/phase-completions/TENANT-SERVICE-ENTERPRISE-AUDIT-2026-07-22.md` claiming 23 findings (F1-F23) with a fix batch applied — this session treated every one of those claims as unverified and re-checked the ones in scope live; results are folded into the findings below with explicit confirmation status.

## Summary

Tenant Management is in materially good shape and the prior 07-22 audit's claims held up under independent live re-verification: tenant CRUD/provisioning, suspension/closure enforcement (both DB-side and live-tested via real login + real API calls, including on an already-issued JWT with no wait for cache expiry), branch/warehouse city-state persistence, org settings save, SSO config CRUD, cross-tenant password reset, the platform-operator/tenant-admin authorization boundary, tenant-scoped list isolation, and audit logging on lifecycle+config mutations all worked exactly as advertised when exercised against the live stack. The real-MinIO provisioning integration test initially appeared broken (timeout, then a "bucket unreachable" error) but that traced to a test-harness environment-variable format mistake on this session's part (`MINIO_ENDPOINT` needs a bare `host:port`, not a URL) — once corrected, all 60 tenant-service tests pass including the real-MinIO round-trip. The module's genuine, still-open gaps are the ones the 07-22 audit already flagged as deliberately deferred: no rollback/resume on a failed provisioning run, decorative plan-based feature gating, dormant RLS as the only systemic cross-tenant-leak backstop, and an in-memory (not Redis-backed) gateway rate limiter that under-enforces across replicas. No new critical bugs were found in this pass.

## What Works (verified live)

- **Tenant CRUD & provisioning**: as PLATFORM_OPERATOR, listed 25 existing tenants (`GET /api/tenant/admin/tenants`), viewed tenant 2 detail, and created a brand-new tenant (`POST /api/tenant/admin/tenants`, id 92) end-to-end. All 12 provisioning steps completed (`CREATE_RECORD` → `SEND_WELCOME_EMAIL`), `provisioningStatus: COMPLETE`. Confirmed in Postgres directly: 13 default roles seeded (`OWNER`, `ADMIN`, `SALES_MANAGER`, ... `SUPER_ADMIN`), 1 admin user, 1 Head Office branch. - **Suspension enforcement — real, not just a DB flag**: suspended test tenant 92 (`PATCH /admin/tenants/92/suspend`), then immediately (1) attempted a fresh login as its admin user → blocked with `403 TENANT_SUSPENDED`; (2) reused an access token minted _before_ suspension against both tenant-service and sales-service → both blocked with the same `403 TENANT_SUSPENDED`, no wait for the documented 60s cache TTL (suspend clearly does a synchronous invalidation, not just a passive expiry). Reactivated (`PATCH /activate`) and confirmed `suspendedAt/suspendedBy/suspendedReason` were cleared to real `null` (not left stale) — this directly confirms the 07-22 audit's F2 fix claim was really shipped, not just documented as shipped. ## Bugs/Gaps Found

None newly discovered as Critical/High in this pass's live-tested surface. The genuine open gaps below are all pre-existing and already tracked by the 07-22 audit; re-stated here with this session's own confirmation status.

### Confirmed still-open (re-verified, not fixed)

- **No rollback/resume on fatal provisioning failure** (07-22's F5). Confirmed by the tenant list itself: several pre-existing tenants from earlier sessions sit permanently in `PROVISIONING`/`FAILED` or `PROVISIONING`/`ADMIN_CREATED` state (e.g. tenant IDs 5, 20, 38-43, 89, 90 — visible in the live `GET /admin/tenants` response this session pulled). There is no API path to retry or clean these up short of direct DB access. **Business impact**: any transient MinIO/ES hiccup during provisioning leaves permanent debris and no self-service recovery; an operator has to notice and manually intervene. **Severity: Medium** (doesn't block new tenants, but accumulates orphaned rows and offers no recovery UX).
- **Non-fatal provisioning steps can leave a tenant ACTIVE with silently missing data** (07-22's F4) — Chart-of-Accounts seeding, ES indices, and welcome email are still fire-and-forget (confirmed by reading `TenantProvisioner.ts`); not re-tested live (would require deliberately breaking ES/CoA seeding mid-provisioning). **Severity: Medium**, deferred by design pending a business decision per the 07-22 audit's own framing.
- **Rate limiting is in-memory/per-pod** (07-22's F16) — indirectly confirmed live: this session's own testing traffic against the gateway triggered a 429 (`Rate limit exceeded, retry in 59 seconds`) after a burst of authenticated requests, confirming the limiter is real and active, but it's still not Redis-backed (confirmed by reading `apps/api-gateway/src/app.ts`, which registers `@fastify/rate-limit` with no `store` option) — with the documented 2-10 replica HPA, effective platform-wide throughput is `limit × replica_count`, not the intended single limit. **Severity: Medium**, operational/scaling concern rather than a correctness bug.
- **Plan-based feature-flag gating is decorative** (07-22's F7/F8) and **RLS is fully dormant** (07-22's F10) — not re-verified live this session (both are large, cross-service architectural gaps outside a single-module audit's practical scope), but nothing found in this pass contradicts the prior audit's characterization. Flagged as still-open per that audit, not independently re-confirmed here.

### New observations (not bugs, but worth flagging)

- `PUT /branches/:id` and `PUT /organization` both require the **full** schema payload (no partial-update/PATCH semantics) — a request omitting a required field (e.g. `code` on branch, `orgName` on org settings) returns a generic `422 Required` that is easy to misdiagnose as the old "field silently discarded" bug class. Both current frontend forms (`BranchFormPage.tsx`, `OrganizationPage.tsx`) always send the required fields, so this isn't user-facing today, but any future API consumer (a script, a mobile client, an AI agent calling the API directly) that sends a partial body will hit this. Not scoring this as a bug since the documented/enforced contract is "full replace," just noting the sharp edge.
- Leftover tenant-management test debris pre-dates this session (tenant IDs 5, 6-13, 20, 25-27, 34-43, 89, 90 are all named "QA .../Test .../MinIO Real Co." etc. from prior audit sessions) — none of it was created or left behind by this session; noted here only so a future cleanup pass doesn't mistake it for this audit's output.
