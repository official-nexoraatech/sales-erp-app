# Audit Logs Module — Production Readiness Audit (2026-07-25)

Scope: the general-purpose, cross-cutting audit trail — `apps/web-frontend/src/pages/admin/AuditLogPage.tsx`
backed by `GET /admin/audit-logs` in `apps/auth-service/src/routes/audit-log.routes.ts`, writing to the shared
`audit_log` table (`packages/db-client/src/schema/index.ts`) via `PlatformAuditLogger`
(`packages/platform-sdk/src/audit.ts`), called as `ctx.audit.log(...)` from route handlers across services.
This is distinct from `SecurityAuditLogPage.tsx` (login/security events — audited separately). All findings
below were verified live against the running stack (gateway :3000, tenant 2 "QA E2E Test Co") plus source
review of every service that imports `@erp/db`'s `auditLog` table or `PlatformAuditLogger`.

## Summary

The general audit log is a real, working, single append-only Postgres table (`audit_log`) with a genuine
paginated/tenant-scoped/entity-filterable REST endpoint, RBAC-gated to admin-tier roles, and no route anywhere
in the codebase that updates or deletes an individual entry (only a scheduled archive-then-purge job for
records older than 1 year). Live volume in the QA tenant is 756 rows and pagination/filtering work correctly
against that data. Where it's wired, before/after capture is genuinely good — invoice status changes, org
settings edits, and customer updates all show real old-value → new-value diffs with a `changedFields` array.

However, coverage is inconsistent and one entire module is completely unlogged: **the Purchase module
(purchase-service) never calls the audit logger at all** — Purchase Orders, GRNs, Purchase Returns, Supplier
Payments, Requisitions, RFQs, Landed Cost, and Expenses produce zero audit trail, despite all of these being
financially significant approval workflows. Separately, Inventory's approval lifecycles (Stock Adjustment
submit/approve/cancel, Stock Transfer update/submit/approve/dispatch/receive/cancel) are logged only at
creation — the actual approve/status-change events, which are the maker-checker control points, are silent.
The frontend's entity-type filter dropdown is also badly out of date, hardcoding only 4 of the ~25+ real
entity types actually present in the table, and the backend query supports no action-type or user filter at
all despite the task's compliance framing implying that's expected. There is no export capability.

## What Works (verified live)

- **Real backend, real data**: `GET /admin/audit-logs` returns paginated, tenant-scoped rows from a genuine Postgres table; live volume 756 rows for tenant 2.
- **Filtering**: `entity` query param works correctly (verified against `invoice`, `journal`, `account`, `GSTR2A`, `STOCK_ADJUSTMENT`, etc. — each returns the correct filtered subset and `totalElements`).
- **Pagination**: `page`/`limit` params correctly slice `ORDER BY created_at DESC`; `totalElements` from a separate `count()` query matches. Indexed on `(tenant_id, created_at)`.
- **Before/after capture, where wired**: invoice `STATUS_CHANGE` row (id 882) shows `beforeData:{status:"DRAFT"}` → `afterData:{status:"CONFIRMED", invoiceNumber:"INV/26-27/00006"}` with `changedFields:["status","invoiceNumber"]` — a real, correct diff, not just "record updated."
- **RBAC**: `STAFF` role → `403 Forbidden — missing permission: one of VIEW_AUDIT_LOG, AUDIT_LOG_VIEW`. `AUDITOR` role → `200`. Confirmed via role-defaults.ts that only OWNER/ADMIN/SUPER_ADMIN (wildcard), ACCOUNTANT, ACCOUNTANT_SUPERVISOR, AUDITOR hold this permission by default — genuinely admin/compliance-tier gated, not broadly granted.
- **Multi-tenant isolation**: the route hard-scopes every query to `request.auth.tenantId` from the JWT — no tenant-crossing query parameter exists. Cross-checked against `apps/sales-service/src/__tests__/audit-trail.test.ts`'s live-DB isolation test (tenant A query returns zero tenant B rows).
- **Immutability**: `grep -rn "\.delete(auditLog)\|\.update(auditLog)"` across `apps/` and `packages/` finds no user-facing route that mutates or deletes an existing row. The only delete is a scheduled system job (`platform.audit-log-archive` in `apps/scheduler-service/src/jobs/system-jobs.ts:1196-1236`) that runs monthly, archives rows older than 1 year to object storage first, then deletes only that archived batch — a legitimate retention policy, not a tamper path. Consistent with the schema's own comment: "Audit Log (Append-only — never UPDATE or DELETE per §13 rule 4)".

## Bugs / Gaps Found

1. **[CRITICAL] Purchase module writes zero audit log entries, ever.** No route in `apps/purchase-service` calls `ctx.audit.log`/`PlatformAuditLogger` anywhere — confirmed by both static grep and live queries returning `totalElements:0` for every purchase entity type, despite real POs/GRNs/Returns/Supplier Payments existing in this environment. Business impact: PO approvals, GRN approvals (which trigger stock+accounting postings), Purchase Return approvals, and Supplier Payments — all financially significant, all requiring maker-checker traceability — leave no audit trail. In a real compliance/fraud-investigation scenario, "who approved this ₹X purchase order and when" is unanswerable from the audit log.

2. **[HIGH] Inventory's approval/status-change lifecycle is not logged, only creation is.** Stock Adjustment `/submit`, `/approve` (the actual maker-checker gate for high-value adjustments), and `/cancel` — and Stock Transfer's `/submit`, `/approve`, `/dispatch`, `/receive`, `/cancel` (6 of 7 mutating routes) — call no audit logger. Only the initial `POST` create is logged. Business impact: an adjustment or transfer's full lifecycle (who approved it, when it was dispatched/received/cancelled) is invisible; only "it was created" is on record.

3. **[MEDIUM] Accounting journal/account entries never populate `entityId`.** `journal.routes.ts` CREATE/REVERSE and the COA seed action put the real identifier only inside a free-form `metadata` JSON blob (`{journalId: "01K..."}` or `{count:70}`), never in the `entity_id` integer column the schema and UI are built around. This breaks entity-based filtering/joining for the entire Accounting module in the audit log — you cannot look up "all audit events for journal #123" the way you can for `invoice #129`.

4. **[MEDIUM] Frontend entity-type filter is stale/incomplete.** `AuditLogPage.tsx` line 24 hardcodes `ENTITY_TYPES = ['', 'invoice', 'sales_return', 'customer', 'item']` — only 4 of the ~25 real entity types actually written to the table (missing `STOCK_ADJUSTMENT`, `STOCK_TRANSFER`, `journal`, `account`, `GSTR1/2A/3B/9`, `payroll_run`, `employee`, `branch`, `organization_settings`, `campaign`, `webhook_subscription`, `supplier`, `warehouse`, `quotation`, `payment`, etc.). A user auditing anything outside those 4 types must page manually through all 756+ rows with no filter — impractical at real-world volume.

5. **[MEDIUM] No action-type or actor/user filter on the backend at all.** `QuerySchema` in `audit-log.routes.ts` only accepts `entity`, `from`, `to`, `page`, `limit` — no `action` (CREATE/UPDATE/DELETE/STATUS_CHANGE/APPROVE...) and no `userId`/actor filter. For a compliance tool whose core use case is "show me everything user X did" or "show me every DELETE last month," this is a materially incomplete query surface. (The frontend also exposes no date-range UI despite the backend supporting `from`/`to`.)

6. **[LOW] Inconsistent `actorEmail`/`ipAddress` population.** Some routes (invoice, organization_settings) populate `actorEmail`/`ipAddress` on every call; others (Stock Adjustment create, all journal/account entries) leave both `null`. The row does carry the real `userId` column, but the frontend's `AuditLogRow` type/UI never displays `userId` — only `actorEmail` — so any row with a null `actorEmail` renders as "Actor: —" in the UI with no way to identify who acted, even though the backend actually knows.

7. **[LOW] No export capability.** No CSV/Excel/PDF export exists on `AuditLogPage.tsx` or the backend route (unlike Reports, which has real xlsx/csv export). Many real-world ERP compliance requirements (SOX, statutory audits) expect exportable audit trails; this is a straightforward gap to flag, not necessarily a blocker.

8. **[LOW] No cross-tenant audit log viewer for platform operators.** Logging in as `operator@platform.local` (tenant 1, PLATFORM_OPERATOR role) against `GET /admin/audit-logs` returns `403 Forbidden — missing permission`. The route has no tenant-override parameter even if the permission were granted — a platform operator investigating a specific tenant's incident has no way to view that tenant's general audit log short of direct DB access. (Out of this audit's core scope but worth flagging alongside the tenant-isolation finding, which is otherwise correctly enforced.)

## Readiness Score: 58/100

**Justification.** The plumbing is solid — real append-only table, real RBAC gate, real tenant isolation,
genuinely good before/after diffing where it's wired, and a legitimate archive-then-purge retention job
instead of ad-hoc deletion. That's a good foundation. But "general audit log" as a compliance feature is
graded on completeness of coverage, and this fails there in a way that matters: an entire module (Purchase)
is 100% dark, and the two other modules with real maker-checker approval workflows (Stock Adjustment, Stock
Transfer) only log the create step, not the approval/status-change events that are the actual point of an
audit trail. Combined with a frontend filter UI that's unusable for most of what actually gets logged, no
action/user filter, and no export, this is not yet a trustworthy single source of truth for "who did what,
when" across the whole ERP — which is exactly what this feature is supposed to be. Fixing the Purchase-module
gap and the two approval-lifecycle gaps would likely move this to the 80s; the filter/UX/export items are
real but secondary.
