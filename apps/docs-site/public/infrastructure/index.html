Infrastructure & Dependency Audit

Twelfth module, and the only one about the system itself rather than a business capability inside it. Built from a direct, four-pass codebase audit (external integrations, environment variables, dependency health, and K8s/Helm/CI tooling) rather than from planning documents — every claim on these pages traces to a file path, config key, or container definition in this repository, verified 2026-07-19.

The short version: this stack is unusually complete for its stage. Real observability, a real tested backup/DR process, and a genuinely strict CI security pipeline already exist. The gaps that remain are specific and fixable — mostly concentrated at the edge of the cluster (ingress, TLS, network policy) rather than in the application layer itself.

4 real third-party APIs wired 0 payment gateway / APM / analytics SaaS in use 19 self-hosted infra containers ~135 env vars in code vs. 78 documented 1 moderate, dev-only CVE in the whole tree 2 frontends with no production Dockerfile

What's genuinely production-shaped already

Observability is real, not scaffolded

Prometheus + Alertmanager + Grafana (two dashboards already provisioned: erp-overview.json, erp-hardening.json) + Loki (via a custom @erp/logger transport — no Promtail sidecar needed) + Jaeger tracing through OpenTelemetry, wired into every one of the 15 backend services.

Backup & DR is real and tested, not theoretical

A daily automated job (pg_dump + Redis SAVE + MinIO mirror), an optional encrypted offsite copy, Pushgateway metrics, and a written runbook with a validated RTO < 30 min / RPO < 15 min target and a quarterly drill cadence. See Infrastructure Components.

CI security posture is strong

Semgrep SAST, Trivy image scanning, Snyk, a full-history TruffleHog secret scan, and a pnpm audit gate all run on every push, alongside lint/type-check/test/E2E. See CI/CD & Deployment.

The three India-specific integrations that actually matter for a GST-compliant retail ERP are real

MSG91 SMS, SendGrid email (with a genuine Mailhog dev fallback), and the NIC e-Invoice/e-Way Bill government APIs — complete with sandbox/production auto-switching and IRN retry logic. Not stubs. See External Services.

What needs attention before a production cutover

Vault secrets are wired two incompatible ways, and neither reaches a running pod

Kubernetes injects secrets via a Vault Agent sidecar that writes to /vault/secrets/db, but no container entrypoint sources that file. Separately, the app's own loadConfigWithSecrets() expects VAULT_ADDR/VAULT_TOKEN to talk to Vault directly over HTTP — neither is set in any k8s manifest or the Helm chart. On a real cluster today, DATABASE_URL and JWT_PRIVATE_KEY would not resolve at all once NODE_ENV=production is set.

NetworkPolicy only covers one of fourteen services

Only auth-service has explicit allow-rules against the default-deny-all policy in infrastructure/k8s/network-policy.yaml. The other 13 backend services would be unable to reach Postgres, Redis, or Kafka if this policy were enforced as-is on a real cluster.

No Ingress resource exists anywhere

cert-manager's three ClusterIssuers are fully scaffolded but bound to nothing — no domain, no TLS termination path, no reverse proxy in front of the cluster. erp-staging.nexoraatech.com is referenced by the CI deploy job's environment URL, but nothing in the repo's IaC actually serves that hostname.

web-frontend and pos-frontend have no Dockerfile at all

Every one of the 15 backend services has a production multi-stage Dockerfile. The two user-facing apps have none — no containerized build, no static hosting config, no CDN setup.

Istio policies are scaffolded, not installed

The authorization and mTLS policies in infrastructure/istio/ assume a control plane that doesn't exist anywhere in this repo's IaC. Treat mesh-level mTLS as unenforced until that changes.

None of this is disqualifying — it's the normal shape of a system that built its application layer, observability, and security tooling before its cluster networking and edge layer. The Known Issues & Punch List page turns this into an ordered action list.

notification-service's three channels, in detail

All three live in apps/notification-service/src/domain/channels/ and are instantiated unconditionally at startup regardless of whether real credentials exist:

  • SmsChannelProvider.ts — POSTs to MSG91's real API. No dev fallback: a blank/placeholder MSG91_AUTH_KEY genuinely calls MSG91 and fails, it doesn't quietly no-op.
  • EmailChannelProvider.ts — has a real dev fallback. If the API key doesn't start with SG., it routes through an SMTP transport to Mailhog instead of calling SendGrid's real API.
  • WhatsAppChannelProvider.ts — POSTs to Meta's Graph API. Same no-fallback behavior as SMS.
4 webhook-verification secrets exist in code with zero documented setup

SENDGRID_WEBHOOK_PUBLIC_KEY, WHATSAPP_APP_SECRET, WHATSAPP_WEBHOOK_VERIFY_TOKEN, and MSG91_WEBHOOK_SECRET are real, tested code (see webhookVerification.test.ts) but aren't in .env.example — see Environment Variables.

gst-service's NIC integration, in detail

EInvoiceService.ts and EwayBillService.ts both branch purely on NODE_ENV === 'production' to pick sandbox vs. real NIC URLs — no manual environment flag to forget. Both throw a clear NIC_NOT_CONFIGURED business error if NIC_API_KEY is unset, and IRN generation has a real retry mechanism (retryPendingIrns(), run every 15 minutes by scheduler-service, up to 5 attempts) rather than failing silently on a transient NIC outage.

Specific bugs and doc gaps worth fixing directly

JWT TTL variables silently do nothing

.env.example documents JWT_ACCESS_TOKEN_TTL/JWT_REFRESH_TOKEN_TTL, but auth-service — the only service that issues tokens — actually reads JWT_ACCESS_TOKEN_TTL_SECONDS/JWT_REFRESH_TOKEN_TTL_DAYS. Setting the documented vars has zero effect on real session length.

Two unrelated "from" address vars exist under near-identical names

SMTP_FROM_ADDRESS (auth/notification/tenant-service) is separate from the documented SMTP_FROM (report-service's scheduled-report emailer only) — easy to set one and assume it covers both.

Local dev port mismatch

docker-compose.yml maps Postgres primary/replica to host ports 5435/5436 (PgBouncer on 5434); .env.example's DATABASE_URL/DATABASE_REPLICA_URL reference 5432/5433. A fresh clone following the example file literally will not connect.

Vault env vars are required by app code but never set in any k8s manifest or the Helm chart

Reinforces the double-wiring gap on the Summary page — this isn't just a config doc gap, it's the exact env var that will crash-loop every service in production the moment NODE_ENV=production is set without also fixing the Kubernetes side.

Dead variables — documented, never read anywhere in code

  • REDIS_CLUSTER_NODES — no Redis Cluster client exists anywhere; the app only ever uses single-node REDIS_URL.
  • OTEL_SERVICE_NAME, OTEL_TRACES_EXPORTER — the OTLP exporter and service name are hardcoded per-service in packages/platform-sdk/src/telemetry.ts, not read from env.

CI/CD & Deployment

The GitHub Actions pipeline (.github/workflows/ci.yml) is genuinely mature. What's missing sits at the edge — registry, secrets, and networking are solid; the ingress/TLS layer between the cluster and the internet doesn't exist yet.

Pipeline stages — all real, all currently running

  1. Lint / format / type-check

    Plus a dedicated guard that fails the build if compiled artifacts are ever committed under packages/*/src.

  2. Test with coverage gate (≥80%)

    Real Postgres + Redis service containers, plus a separate Playwright E2E smoke job for both frontends.

  3. Security gates

    Semgrep SAST (OWASP + Node + TS rulesets), Trivy container scan (fails on critical/high), Snyk, TruffleHog full-history secret scan, pnpm audit --audit-level=high.

  4. Build & push

    15-service Docker build matrix to GHCR, tagged by branch/PR/semver/SHA.

  5. Manual load testing

    k6, dispatched on demand against a live target, with an automatic P95-regression gate — fails if any endpoint exceeds its target by more than 20%.

  6. Staging deploy

    Triggered by a v* git tag: applies infrastructure/k8s/ via kustomize, waits on all rollouts in parallel, runs a post-deploy smoke test, and auto-rolls-back every service on any failure.

  7. GitLab mirror

    A separate workflow force-pushes main to GitLab.com on every push — a pure backup/BCP mirror, not a second CI system.

Adding a new backend service to CI is entirely manual, in four separate places

There's no automatic discovery of services in the pipeline — a new service must be added by hand to the Docker build matrix, the container-scan matrix, and two separate hardcoded service-name lists inside the staging-deploy job's rollout and rollback steps. Miss one and that service silently doesn't get its intended coverage.

What production deployment is actually missing

No Ingress controller and no Ingress resource

https://erp-staging.nexoraatech.com is referenced by the CI environment URL, but nothing in the repo's IaC actually serves that hostname.

NetworkPolicy locks down 13 of 14 services with no allow-rules

Would need extending before enforcement is safe to turn on for real — see Infrastructure Components.

Vault secret injection doesn't reach a running pod today

Needs a real delivery path chosen: a Vault Agent init-container that's actually sourced, the Vault CSI provider, or falling back to Kubernetes Secrets synced from Vault via External Secrets Operator.

No production build/hosting path for either frontend

Needs a Dockerfile + nginx, or static hosting via S3/CloudFront/Cloudflare Pages, added before a real cutover.

Cost Plans & OSS Alternatives

Ranges, not quotes — actual pricing depends on region, negotiated cloud discounts, and real transaction/message volume. All three plans below assume the CI/CD, observability, and backup layers already built in this repo are reused as-is; the delta between plans is almost entirely managed-vs-self-hosted data infrastructure and redundancy, not new integrations.

Starter — self-hosted, single region

$120–260/mo. Development, pilot, or a single small retail chain. One or two beefy VPS instances running the whole docker-compose stack.

  • 1–2× 8vCPU/16GB VPS (Hetzner/DigitalOcean) — $80–160
  • MSG91 pay-as-you-go, low volume — $10–20
  • SendGrid free tier (100/day) — $0
  • NIC e-invoice via a low-tier GSP — $20–50
  • Domain + Let's Encrypt TLS — ~$1/mo amortized
  • Offsite backup bucket — $5

Professional — managed cloud, single region, HA

$800–1,600/mo. A medium retail business running real transaction volume across several branches. Managed data services, real HPA autoscaling.

  • Managed Kubernetes, 3 nodes — $150–300
  • Managed Postgres, HA — $60–200
  • Managed Redis — $30–60
  • Kafka, self-hosted on cluster or managed — $0–300
  • Elasticsearch, self-hosted OpenSearch or Elastic Cloud — $0–200
  • Sentry Team + Grafana Cloud — $26–75
  • MSG91 + SendGrid Essentials + WhatsApp BSP — $150–300
  • GSP production contract — $50–150

Enterprise — multi-AZ, DR, security hardened

$5,000–14,000/mo. Multi-branch/multi-tenant at scale, contractual uptime SLAs, compliance obligations.

  • Multi-AZ managed Kubernetes, autoscaled — $500–1,500
  • Multi-AZ Postgres w/ read replicas — $400–1,000
  • Managed Kafka (Confluent/MSK, dedicated) — $500–2,000
  • Elastic Cloud, production tier — $500–1,500
  • HCP Vault Dedicated (or hardened self-hosted HA Vault) — $1,500+
  • Datadog or Grafana Cloud Pro + PagerDuty paid — $500–1,500
  • WAF/CDN (Cloudflare Enterprise) — $200–2,000
  • Cross-region DR + compliance tooling — $200–500

Dependency Audit

Full workspace scan: root + 18 apps/* + 8 packages/* manifests, the resolved lockfile, and a live pnpm audit run.

Security

1 moderate finding, 0 high/critical

esbuild ≤0.24.2 dev-server request forgery, reached only through drizzle-kit's dev-only migration CLI — never shipped in any of the 15 production Docker images. Already below CI's --audit-level=high gate.

Version consistency

No real cross-service conflicts. fastify, kafkajs, drizzle-orm, vitest, vite, and React each resolve to a single version workspace-wide; apparent ioredis/jose/zod range differences collapse to one lockfile version each (partly thanks to a root pnpm.overrides pin on ioredis).

Confirmed unused (6 found)

  • ulid declared in 10 services, actually imported in only 6 — dead in auth, hr, scheduler, tenant-service
  • zod in api-gateway (pure proxy, no validation layer)
  • @erp/utils in inventory-service (every sibling service uses it; this one doesn't)

Supply-chain note

xlsx is sourced from a CDN tarball, not npm

Used in gst-service, report-service, scheduler-service, and tools/migration — SheetJS's own distribution choice after deprecating npm releases. Consequence: pnpm audit/Snyk/Dependabot cannot scan it at all, and an outage at cdn.sheetjs.com would break pnpm install for those 4 packages with no fallback mirror.

Everything else checked and found clean

No deprecated/abandoned packages (no request, moment, node-sass, tslint). TypeScript strictness is uniform across all 17 tsconfigs. Node 20 is consistent across .nvmrc, root engines, CI, and all 15 Dockerfiles with zero drift. The CI guard against committed compiled artifacts under packages/*/src is present and active. The only manifest hygiene issue found outside the workspace itself: tools/migration and tools/uat-seed (outside the pnpm workspace glob) declare @types/node ^22 against a Node 20 runtime target.

Known Issues & Punch List

The final page of this module — ordered by what actually blocks a production cutover versus what's a cost or hygiene optimization.

Must fix before production

  1. Wire Vault end-to-end

    Pick one delivery mechanism — a Vault Agent sidecar actually sourced by the entrypoint, the Vault CSI driver, or External Secrets Operator — and confirm it end-to-end. Today neither existing half-wired path reaches a running pod.

  2. Extend NetworkPolicy to the other 13 services

    Before enforcing default-deny in a real cluster, every service needs the same treatment auth-service already has in infrastructure/k8s/network-policy.yaml.

  3. Stand up an Ingress controller

    Bind it to the existing cert-manager ClusterIssuers and a real domain — currently nothing serves the hostname the CI deploy job already references.

  4. Build a production path for both frontends

    Dockerfile + nginx, or static hosting via a CDN — currently the only two apps in the monorepo with neither.

  5. Fix the env var documentation mismatches

    The JWT TTL var names and the SMTP_FROM/SMTP_FROM_ADDRESS split, before anyone configures a production environment from .env.example alone.

Should add — cheap, high value

Sentry or GlitchTip for error tracking

The single biggest observability gap relative to effort — see Dev, Ops & Admin Tooling.

pgAdmin/Adminer, RedisInsight, and a Kafka UI

All free, all currently missing from docker-compose.yml.

An OpenAPI spec per service

@fastify/swagger closes the "no Postman/Swagger anywhere" gap cheaply.

Cost optimization opportunities

  • Drop Snyk — Trivy + Semgrep + pnpm audit already cover the same ground in CI today.
  • Stay on self-hosted Elasticsearch/OpenSearch and Kafka rather than migrating to Elastic Cloud/Confluent Cloud unless operational load genuinely exceeds in-house capacity — the Professional-tier estimate already assumes this.
  • Migrate the 4 xlsx-consuming packages off the CDN tarball dependency once SheetJS ships a scannable npm release, to close the one real supply-chain blind spot found.

Safe to remove
